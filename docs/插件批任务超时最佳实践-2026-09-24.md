# 插件批任务超时最佳实践（PLUGIN_TIMEOUT 与 util/pool）

更新时间：2026-09-24。
状态：L0（止血）、L1（可观测）、L2（可取消）已落地并验证；L3（结果收集重构）未落地，理由见第六节。
适用版本：`main` 分支 `0be55bd` 起（该版本的 `util/pool/worker_pool.go` 与社区 PR `fish2018/pansou#153` 的 base `6f4e09f` 逐字节相同）。

## 一、结论摘要

1. `PLUGIN_TIMEOUT` 原先只影响“返回哪些结果”，不影响“多久返回”，耗时等于最慢插件。全量 72 插件实测：基线 41.07s → 改造后 3.03s。
2. 除耗时问题外还存在一条概率性永久挂死路径：worker 发送结果时不响应 `ctx`，结果队列写满后 `Close()` 的 `wg.Wait()` 永不返回，请求连同承载它的 goroutine 一起卡住。
3. 社区 PR `#153` 的形态可以合并，它把上述两处都修掉了。本仓库在其思路上补了三处：用 `ctx` 状态而不是结果数量判断超时、把异步关闭做成显式 API 并去掉异步路径里没有读者的 `close(results)`、给 worker 加 `recover`。
4. 根治手段是把取消信号真正传到任务与插件：批任务的 `ctx` 现在会随 `ext` 进入插件基类，插件在超时点立刻返回，而不是等自己的响应超时或内部重试。

## 二、现状与缺陷

### 2.1 原有代码事实

- `util/pool/worker_pool.go`：`ExecuteBatchWithTimeout` 创建带超时的 ctx，随后 `defer pool.Close()`。
- `Close()` 的展开是 `cancel()` → `close(taskQueue)` → `wg.Wait()` → `close(results)`，等待 worker 全部退出这步发生在调用方返回之前。
- worker 循环为 `select { case task, ok := <-p.taskQueue: ...; case <-p.ctx.Done(): return }`，但任务体与结果发送都在 select 之外：`result := task()` 之后直接 `p.results <- result`。
- 通道容量：`taskQueue` 与 `results` 均为 `maxWorkers * 2`；`maxWorkers` 收敛为 `min(传入并发, 任务数)`。
- 调用点两处：`service/search_service.go` 插件搜索（并发来自 API 的 `conc` 参数，缺省 `DefaultConcurrency = 频道数 + 插件数 + 10`）与 TG 频道搜索（传入 `len(channels)`）。

### 2.2 三个缺陷

**缺陷一：超时只丢结果，不缩短耗时。**
`GetResults` 在 ctx 到点后按时返回，但紧接着的 `pool.Close()` 会 `wg.Wait()`，而任务体不可中断，只能等最慢的插件自己跑完。

**缺陷二：worker 发送结果时无 ctx 保护，可能永久挂死。**
ctx 到点后没有人再读 `results`。worker 若在其缓冲写满时阻塞在 `p.results <- result`，就再也回不到 select，`ctx.Done()` 永远不会被观察到，`wg.Wait()` 于是永不返回。触发条件是“任务数 > 2 × 并发”且至少一个 worker 在取消后继续跑满缓冲；默认部署下 `maxWorkers = min(默认并发, 任务数) = 任务数`，缓冲为 `2 × 任务数`，走不到这条路径，但 API 的 `conc` 可以把它压任意小。

**缺陷三：超时后完成的结果被丢弃。**
`GetResults` 返回即定稿。这是原有语义，`BaseAsyncPlugin` 的后台补缓存会在下一轮请求命中，属可接受取舍。

池层（`util/pool` 内直接调度）：

端到端（真实站点，全量 72 个插件，`PLUGIN_TIMEOUT=3`，`CACHE_ENABLED=false`，`refresh=true`，关键词“漫长的季节”）：

| 版本 | 耗时 | 结果数 |
|---|---|---|
| 基线 | 41.07s | 204 |
| L0+L1+L2 | 3.03s | 203 |

改造后服务端日志给出超时批次的真实分布：

```
[worker_pool] 批次超时：已收到 59/72 个结果，其余任务在后台执行
```

59 个任务在超时点返回（走 `BaseAsyncPlugin` 等待路径的插件都已响应取消），剩余 13 个属于“内部同步阻塞、不经过基类等待”的插件，需要在插件内部把请求上下文接上才能真正取消。

TG 频道路径（Dockerfile 里的 110 个频道，经 `https_proxy`/`http_proxy`/`all_proxy` 走本地代理，`CACHE_ENABLED=false`，`refresh=true`）：

| 场景 | 基线 | 改造后 |
|---|---|---|
| `src=tg`，默认超时 | 2.06s / 45 条 | 2.24s / 45 条 |
| `src=tg`，`PLUGIN_TIMEOUT=1` | 1.80s / 1 条 | 1.03s / 0 条 |
| `src=all`（110 频道 + 72 插件），`PLUGIN_TIMEOUT=3` | 4.12s / 217 条 | 3.07s / 205 条 |

`src=tg` 两版结果逐类型一致（quark 15、aliyun 7、123 六条、baidu 5、xunlei 5、115 3、guangya 3、mobile 1），说明频道路径没有回归。`PLUGIN_TIMEOUT=1` 小于频道自身的 4 秒超时，改造后按 1.03s 返回，基线则等到最慢频道跑完（1.80s），证明取消信号在频道路径同样生效。`src=all` 少的 12 条全部是磁力类插件的结果，来自插件侧在 3 秒后才完成的搜索，属于超时截断的正常取舍。

频道路径的取消粒度是 HTTP 层：`PLUGIN_TIMEOUT=1` 时请求返回那一刻只收到 7/110 个结果，其余任务正在被取消的过程中，由后台回收收尾；插件路径同一时刻能收到 59/72（基类 `select` 直接监听 ctx，唤醒更快）。

## 四、方案对比

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. 不等慢任务 | 调用方按超时返回，未收齐时后台关闭；worker 发送加 `ctx.Done()` 分支 | 改动最小，向后兼容 | 慢任务仍占资源；无观测 |
| B. 显式异步关闭 | 拆出 `Shutdown(wait bool)`，异步路径不关结果通道 | 语义显式、可测、可观测 | 仍是“不等” |
| C. 取消信号贯穿任务与插件 | 任务签名带 ctx，插件基类响应取消 | 真正让调用方按超时返回，后台回收降到最低 | 触及池层签名与插件基类 |
| D. 重构结果收集 | 结果按索引落位 + `WaitGroup`/`errgroup` | 消除计数耦合与关闭时序脆弱点 | 重构面最大 |

本次落地 A+B+C；D 见第六节。

## 五、已落地的实现

### 5.1 池层：`util/pool/worker_pool.go`

任务签名带上批任务上下文，worker 执行时把 panic 收敛成本轮“无结果”，发送结果时同时响应取消：

```go
// Task 表示一个工作任务。
// 执行时会收到本次批次的上下文：超时后调用方可以据此提前返回，
// 而不必等不可中断的任务自己结束。
type Task func(ctx context.Context) interface{}

// runTask 执行单个任务，并把 panic 收敛为本轮的“无结果”。
// 插件解析代码属于外部输入处理，单个插件 panic 不应拖垮整个服务进程。
func (p *WorkerPool) runTask(task Task) (result interface{}) {
	defer func() {
		if r := recover(); r != nil {
			fmt.Printf("[worker_pool] 任务 panic 已收敛: %v\n", r)
			result = nil
		}
	}()

	return task(p.ctx)
}
```

关闭语义拆成显式开关：同步关闭保持原行为，异步关闭不再关闭结果通道（没有读者，交给 GC 即可）：

```go
// Close 关闭工作池：等待所有工作者退出后关闭结果通道。
func (p *WorkerPool) Close() { p.Shutdown(true) }

// Shutdown 关闭工作池。
// wait=false 用于超时路径：调用方不等不可中断的任务，回收在后台完成；
// 此时不再关闭 results —— 调用方已停止读取，通道交给 GC 即可，
// 否则后台仍要等任务结束才能关闭通道，goroutine 白白延长存活。
func (p *WorkerPool) Shutdown(wait bool) {
	p.cancel()
	close(p.taskQueue)

	if !wait {
		go func() { p.wg.Wait() }()
		return
	}

	p.wg.Wait()
	close(p.results)
}
```

超时判据与可观测性（`BackgroundReclaims()` 可直接接监控）：

```go
func closeAfterResults(ctx context.Context, pool *WorkerPool, count int) []interface{} {
	results := pool.GetResults(count)

	// 用上下文状态判断是否超时，而不是结果数量：
	// “结果没凑齐”与“已经超时”是两件事，后者才是调用方需要立刻返回的信号。
	if ctx.Err() != nil {
		atomic.AddInt64(&backgroundReclaims, 1)
		fmt.Printf("[worker_pool] 批次超时：已收到 %d/%d 个结果，其余任务在后台执行\n",
			len(results), count)
		go pool.Shutdown(false)
	} else {
		pool.Shutdown(true)
	}

	return results
}
```

### 5.2 插件层：`plugin/plugin.go`

取消信号随 `ext` 传递，而不是保存在插件实例上——同一插件实例会被并发请求共用，存字段会互相覆盖：

```go
// ExtContextKey 是 ext 中承载本次搜索上下文的键。
const ExtContextKey = "_ctx"

// ContextFromExt 取出本次搜索的上下文，未设置时返回 background。
func ContextFromExt(ext map[string]interface{}) context.Context {
	if ext != nil {
		if ctx, ok := ext[ExtContextKey].(context.Context); ok && ctx != nil {
			return ctx
		}
	}
	return context.Background()
}
```

`AsyncSearch` 与 `AsyncSearchWithResult` 的等待段把“响应超时”和“调用方取消”合并到同一处理分支，因此插件在批任务到点时立刻返回，后台搜索继续填充缓存：

```go
	searchCtx := ContextFromExt(ext)

	// 超时或调用方取消：返回空结果，后台继续处理并填充缓存
	pending := func() model.PluginSearchResult { /* 原超时分支的处理 */ }

	select {
	case results := <-resultChan:
		return model.PluginSearchResult{Results: results, IsFinal: true, /* ... */}, nil
	case err := <-errorChan:
		return model.PluginSearchResult{}, err
	case <-time.After(responseTimeout):
		return pending(), nil
	case <-searchCtx.Done():
		return pending(), nil
	}
```

### 5.3 服务层：`service/search_service.go`

任务按新签名接收 ctx，并把 ctx 注入插件 ext 的副本（复制而不是就地写入，避免并发请求互相覆盖）：

```go
	tasks = append(tasks, func(ctx context.Context) interface{} {
		plugin.SetMainCacheKey(cacheKey)
		plugin.SetCurrentKeyword(keyword)

		// 批任务的超时时间通过 ext 传给插件，插件基类据此在到点后立刻返回。
		results, err := plugin.Search(keyword, pluginExtWithContext(ext, ctx))
		if err != nil {
			return nil
		}
		return results
	})
```

TG 频道路径同样接上父上下文：`searchChannel` 保留原签名作为包装，新增 `searchChannelWithContext(parent, ...)`，频道自身的 4 秒超时不变，额外受批任务超时约束。

## 六、未落地：L3 结果收集重构

`GetResults` 按数量从通道收结果，隐含“每个任务恰好发送一次”的强假设。更稳的模型是结果按任务索引落位：

```go
results := make([]interface{}, len(tasks))
var wg sync.WaitGroup
sem := make(chan struct{}, maxWorkers)
for i, task := range tasks {
	wg.Add(1)
	go func(i int, task Task) {
		defer wg.Done()
		sem <- struct{}{}
		defer func() { <-sem }()
		results[i] = task(ctx)
	}(i, task)
}
```

不放在本轮的理由：L0+L2 已经消除了缺陷一、二的触发条件（挂死由“发送响应取消 + 结果通道不再被填满”双重保证），L3 的收益从“修 bug”转为“去掉结构性脆弱点”，而它要改写 `WorkerPool` 的核心数据结构与 `Submit`/`GetResults` 语义，与行为修复混在一次改动里不利于排查。若接受引入依赖，`errgroup` + `context` 是同等效果的现成实现。

## 八、相邻风险

- **插件内部同步阻塞不响应取消。** 走 `BaseAsyncPlugin` 等待路径的插件已能在超时点返回，但插件 `searchImpl` 内部的 HTTP 请求与重试仍会跑完，仅由 `backgroundClient` 的 30 秒超时兜底（实测 72 插件里有 13 个属于这一类）。下一步是让插件把 `req.WithContext(ctx)` 接上，这需要动 `searchFunc` 签名或逐个插件改造。
- **频道路径的超时没有补偿机制。** 插件路径超时后，`AsyncSearch` 的后台搜索仍会完成并写入插件缓存，下一轮请求即可补齐；`searchChannel` 是即时请求，被取消后本轮结果直接消失。实测 110 个频道经代理约 2 秒内完成，因此 `PLUGIN_TIMEOUT` 的有效预算应不低于频道的最慢响应时间，否则 `src=tg`/`src=all` 会系统性缺少频道结果。若需要频道路径也具备补齐能力，需要在 `searchTG` 之上加一层与插件同级的缓存。
- **`ExecuteBatch`（无超时版）仍没有 ctx 保护。** 若结果数与任务数不匹配，`GetResults` 会死等；`service` 未使用该路径，改造成 L3 的落位模型可一并消除。
- **`PLUGIN_TIMEOUT` 下限未校验。** 取值过小时超时会成为常态，插件缓存长期停留在“不完整”状态。配置加载时对过小值给出告警，并用 `BackgroundReclaims()` 的增长速率作为调参依据。

## 九、验收标准

- `PLUGIN_TIMEOUT=5` 且启用含慢插件的全量插件搜索时，`src=plugin` 的 P95 耗时不高于 6s。本轮单次实测 3.03s（`PLUGIN_TIMEOUT=3`）。
- 长稳运行 1 小时、持续 `refresh=true` 请求，goroutine 数相对基线的波动收敛在并发量级，无单调增长。池层已有对应断言，长稳观察建议在部署环境用 `BackgroundReclaims()` 与 `runtime.NumGoroutine` 一起看。
- `go test -race ./util/pool/` 重复 10 次通过，其中挂死用例零失败。

## 附录：复现环境

- 池层：在 `util/pool` 包内直接调用 `ExecuteBatchWithTimeout`，用测试断言耗时与 goroutine 数；缓冲容量为 `maxWorkers*2`。
- 端到端：用同一份源码分别构建“改动前/改动后”两个二进制，以相同 `ENABLED_PLUGINS`、`PLUGIN_TIMEOUT`、`CACHE_ENABLED=false` 启动，请求 `/api/search?src=plugin&refresh=true` 对比耗时。改动前的二进制应在改动前导出（例如 `git stash` 后构建），避免用修改后的工作区反推基线。
- 慢插件对照：把沙盒插件注册进源码副本、固定阻塞数十秒，可稳定复现“等待最慢任务”与“结果队列写满”两条路径，且不污染上线分支。
