# TG 快速兜底搜索：性能分析、技术债与优化方案

日期：2026-09-24。范围：`src=tg` 频道搜索链路（110 个频道）。方法：本地实测（真实 t.me 页面、代理与直连两种环境）+ 第三方调研。
结论前提：该链路定位是"快速兜底"——在 4 秒预算内给出尽可能完整的基本资源数据，延迟优先。

## 一、结论摘要

1. **4 秒预算在网络侧有 2 倍余量**：110 频道全部返回耗时 1.8–2.5s（单次）、并发三个热词时最慢 3.43s，0 失败、0 个 429。
2. **端到端耗时的主导因素是网络往返，不是解析**：单请求 RTT 约 1.3s 是硬下界；连接冷启动会额外付 0.75s（冷 1.73s → 热 0.98s）。
3. **CPU 侧耗时最多的是正则匹配，不是 HTML 解析**：pprof 显示 `regexp` 执行占 26–30%（Go 用 RE2，属线性扫描成本，尤其大 alternation），`ExtractPassword` 单项占 24%，而 `x/net/html` tokenizer 只占 4.6%。
4. **解析实现有 10 倍以上空间但收益受体型限制**：第三方复刻 9 种实现后，手写字节扫描 0.20ms/页 vs goquery 1.94ms/页（同场景 10.4×，分配少 47×）；我本机独立测得 0.65ms vs 7.6ms。在 8 核上这笔 CPU 与网络重叠，端到端只值约 3%；在**单核**上值 33%（实测单核 2.88s vs 8 核 1.92s）——单核冷启动会突破 4s 预算（4.45s）。
5. **当前代码有四个真实风险**：残缺结果被无条件写入 60 分钟缓存（已实测复现）、不检查 HTTP 状态码、响应体无大小上限，以及依赖的 `golang.org/x/net v0.41.0` 受 `html.Parse` 二次复杂度 DoS 影响（CVE-2025-47911 / GO-2026-4440，修复版 0.45.0，当前最新 v0.59.0）。
6. **两个"看起来该做"的方向被实测否掉**：连接池调优（HTTP/2 下 110 并发只开 2 条 TCP，非瓶颈）、条件请求/ETag（上游 `cache-control: no-store` 且无验证器，结构性不可用）。

## 二、实测环境

- 机器：Intel i5-8257U（8 逻辑核），Go 1.24.9，macOS。
- 网络：本地代理 `http://127.0.0.1:7897`（与生产同类场景），另有直连对照。
- 语料：Dockerfile 中的 110 个频道；热词 仙逆 / 遮天 / 凡人修仙传 / 兰香如故 / 漫长的季节。
- 样本页面：122–159KB（`?q=` 搜索页，单页 12–20 条消息）。

## 三、网络侧实测

### 3.1 单次搜索（110 频道并发）

| 热词 | 墙钟 | P50 | P90 | P99 | max | 消息数 |
|---|---|---|---|---|---|---|
| 仙逆 | 2.50s | 1.97s | 2.26s | 2.48s | 2.50s | 994 |
| 遮天 | 2.08s | 1.64s | 2.04s | 2.06s | 2.07s | 1019 |
| 凡人修仙传 | 2.06s | 1.73s | 1.99s | 2.03s | 2.06s | 940 |
| 兰香如故 | 1.84s | 1.47s | 1.73s | 1.73s | 1.84s | 559 |
| 漫长的季节 | 1.82s | 1.44s | 1.72s | 1.81s | 1.81s | 378 |

重复采样（仙逆 ×3：1.95 / 1.96 / 2.11s；凡人修仙传 ×3：1.73 / 1.76 / 1.87s）消息数恒定、0 失败。

### 3.2 延迟分布特征

- **分布极窄**（P50≈max），说明瓶颈是"每个请求都要付的共同成本"，不是个别慢频道。
- 最慢的频道共同点：单页满 20 条（下载字节多），印证带宽/传输量相关。
- 并发三个热词（330 请求）时出现长尾：仙逆墙钟 3.43s，但 P99 仍只有 2.00s——**尾部由 1 个频道贡献**。

### 3.3 预算-完整度权衡（本机直连与代理两套数据一致）

| 预算 | 代理环境 | 直连环境 |
|---|---|---|
| 800ms | — | 2.7% |
| 1000ms | 0–3% | — |
| 1500ms | 15–35% | 27% |
| 2000ms | 31–100% | 100% |
| 2500ms | 100% | 100% |

在 pansou 端到端验证（`src=tg`，仙逆，PC 端完整结果 451 条）：

| 池级预算（PLUGIN_TIMEOUT） | 耗时 | 结果数 | 完整度 |
|---|---|---|---|
| 2s | 2.18s | 346 | 76.7% |
| 3s | 3.31s | 451 | 100% |
| 4s（默认行为等价） | 4.03s | 451 | 100% |

**3 秒是当前条件下的甜点**：与 4s 结果完全相同，少花 0.7s。2 秒会丢 23% 的真实数据。

### 3.4 连接与传输

- **HTTP/2 多路复用**：110 个并发请求只建立 **2 条 TCP 连接**（复用 108）。`MaxConnsPerHost=100`、`MaxIdleConnsPerHost=20` 都碰不到 → 连接池调优不是本场景的杠杆。
- **冷热差**：首轮 1.73s、第二轮 0.98s（同一进程内，连接与 TLS 已建立）→ 省 0.75s（43%）。pansou 端到端同样可见：冷启动 3.34–3.47s、稳定态 1.92–1.96s。
- **传输量**：gzip 后单页 19.7–24KB（压缩 5.4–7.1×），110 频道约 2.2–2.6MB/搜索。Go 默认透明解压已生效（不要手动设置 `Accept-Encoding`，否则失去自动解压）。
- **上游响应头**：`server: nginx/1.30.1`、`cache-control: no-store`、`pragma: no-cache`，**无 ETag / Last-Modified**，无 Cloudflare 特征头。
- **限流**：本轮约 2000+ 次请求（含 440 并发、连续突发）**零 429、零 5xx**。User-Agent / Referer / Accept-Language 对结果无影响。

## 四、CPU 侧实测

### 4.1 pprof 热点（4 个真实页面全链路解析）

| 项 | cum | 占比 |
|---|---|---|
| `regexp.backtrack` / `tryBacktrack`（正则回溯） | 710ms | **29.8%** |
| `ExtractPassword` | 570ms | **24.0%** |
| `goquery.NewDocumentFromReader` | 540ms | 22.7% |
| `extractTitle`（其中第 642 行重建 DOM 占 140ms） | 200ms | 8.4% |
| `cascadia.Selector.matchAllInto`（CSS 选择器引擎） | 170ms | 7.1% |
| `x/net/html.Tokenizer.readByte`（HTML 词法分析） | 110ms | **4.6%** |

逐行定位：`regex_util.go:482`（`regexp.MustCompile`）10ms、`:490`（`UrlPasswordPattern.FindStringSubmatch`）20ms；`parser_util.go:642`（为**每条消息**新建 goquery 文档）140ms。

口径修正：Go 的 regexp 是 RE2（Thompson NFA，线性时间，不存在灾难性回溯，见 Russ Cox 原文）。这里的 26–30% 是**正则匹配的常态成本**，主要来自大 alternation（全站网盘链接模式）逐字符扫描，不是"指数爆炸"；治理方向是缩小正则作用范围或改手写扫描，而非"消除回溯"。

### 4.2 解析实现对比（4 个真实样本页，提取结果已用等价性测试校验一致）

| 实现 | 每页耗时 | 每页分配 | allocs/页 |
|---|---|---|---|
| `ParseSearchResults`（现状，goquery 整页 DOM） | 7.6ms | 1.46MB | 13405 |
| `x/net/html` tokenizer 流式遍历 | 1.51ms | 36KB | 535 |
| 手写 `strings.Index` 分块扫描 | **0.65ms** | **3.8KB** | 101 |

等价性：三种实现的消息数（20/20/17/20）与链接数（45/54/17/20）完全一致。
口径提醒：手写版只覆盖"定位消息 + 识别链接"子集，完整替换还需迁移标题/密码提取逻辑。

复刻 `parser_util.go` 真实字段（含 `Html()`/`Text()`/组合选择器）：goquery 路径 1.94ms / 512KB / 6570 allocs，手写路径 **0.20ms / 50KB / 125 allocs**；在 154KB/20 块样本上是 10.4×（时间）/ 8.9×（内存）/ 47×（分配次数）。
110 页并发解析（纯 CPU 墙钟，1→8→32 worker）：goquery 148.6→69.7→59.7ms；Tokenizer 低层 69.9→29.3→28.9ms；手写 24.8→8.2→5.9ms；纯 regexp 455.8→179.1→208.9ms（最慢且尾延迟最差）。
分配来源（alloc_space profile）：DOM 构建约 75%、`Html()` 的重新序列化与二次拷贝约 11.7%、cascadia 选择器编译仅 2.2%（`Find()` 每次编译 matcher 实测只占 0.2%，无反射开销）→ **优化重点是"不建 DOM、不重建 HTML 字符串"，不是缓存选择器**。

### 4.3 正则机制

- 现状：`util/regex_util.go:473/482/502/520` 在 `ExtractPassword` 内部每次调用临时编译；同类在 `service/search_service.go:654/875/984`（per-result）。全仓库统计：**包级预编译 22 处，函数内临时编译 684 处**。
- 微基准：`ExtractPassword` 23.5µs / 111 allocs → 正则提包级后 6.7µs / 4 allocs（**3.5×**）；第三方复刻在迅雷分支下测得 12.6×（3720ns → 296ns）。
- 但在**全链路**基准里无法分辨（34.5ms vs 29.9ms，噪声达 33%）——因为真实语料中多数链接走包级路径，不触发那 4 段编译。**正确的期望是"降 GC 与最坏情况"，而不是端到端提速**。
- 正面发现：编译成本是匹配成本的约 13.6 倍；`MatchString` 962ns/0 alloc vs `FindAllString` 69.5µs/20 allocs（72×）。

### 4.4 extractTitle 去掉 goquery（已完整验证）

| 实现 | 每条消息 | 分配 | allocs |
|---|---|---|---|
| 现状（`goquery.NewDocumentFromReader` 包一层 div） | 57µs | 2.19MB/77 条 | 12148 |
| 手写去标签 + `html.UnescapeString` | **20µs** | 0.81MB/77 条 | **729** |

等价性：77 条真实消息输出 **0 差异**。折算 110 页（2200 条消息）：约省 80ms CPU。

### 4.5 CPU 受限场景的端到端影响

| 环境 | 冷启动 | 稳定态 |
|---|---|---|
| GOMAXPROCS=1 | **4.45s**（突破 4s 预算） | 2.83 / 2.94s |
| 8 核 | 3.34s | 1.92 / 1.93s |

差值 0.96s ≈ 解析（~0.6s）+ 正则（~0.3s），与 pprof 账目吻合。**结论：8 核上解析优化只值约 3%，单核/低配 VPS 上值 33%。**

## 六、优化方案（按端到端收益排序）

**第一梯队：网络侧，改动极小**
1. **预算从"等每频道 4s"改为"池级软截止 ~3s"**：实测结果不变（451 条）、耗时 4.03s → 3.31s（省 18%）。
2. **延长空闲连接保活**（`IdleConnTimeout` 90s → 5–10 分钟，并做成可配）：稳态省 0.75s；对搜索型服务（同 host 高频访问）收益稳定。
3. **软截止 + partial 标记**（对齐 Solr `timeAllowed`/`partialResults` 与 ES `allow_partial_search_results` 语义）：高负载下 2.2s 返回已到结果，剩余不取消、结果回填缓存。实测拥塞时 P99 2.0s、max 3.43s，说明这 1.4s 的尾巴值不回完整度。

**第二梯队：正确性（不做就等于埋雷）**
4. **残缺结果不写缓存**（或按完整度打折 TTL）：已实测的负面缓存污染。
5. **状态码分类 + `io.LimitReader`**：把 429/403/404/超时分开，并防异常大响应。
6. **后台补齐结果回填缓存**：让超时批次的成果可被后续请求复用。

**第三梯队：CPU 侧（低配部署才值钱）**
7. **`extractTitle` 去 goquery**：2.8×、分配 16.7×、输出已验等价，改动约 30 行。
8. **`ExtractPassword` 等 4 处正则提包级**：3.5×、零风险、10 行。
9. **整页解析换 tokenizer 或手写扫描**：11.7×（手写）/5×（tokenizer），但需重写 321 行并保证输出等价——建议先用等价性测试锁定行为（本轮的等价性测试可直接复用）。
10. **热路径正则改手写扫描**：正则回溯占总 CPU 的近三成，是 CPU 侧最大单项；代价是密码/链接识别的边界处理，风险最高，建议最后做。

**解析重写的推荐形态（第三方复刻结论）**
- 首选：**分块定位（`bytes.Index`）+ 字节级字段扫描 + innerHTML 直接切片原文**，不建 DOM、不调 `Html()`。预期单页 1.9–2.9ms → 0.2–1.1ms（-60%~-93%），分配 512KB → 50–59KB（-90%）。风险是结构/属性顺序漂移敏感，**必须配真实页面快照契约测试并保留 goquery 回退路径**（本轮的等价性测试可直接作为契约测试起点）。
- 次选：`x/net/html` Tokenizer **低层 API**（Text/TagName/TagAttr），比手写抗漂移，比 goquery 省约 72% 时间、87% 内存。务必避开 `Token()` 高层 API（内存 3.4×，其上分配占 profile 的 33.9%）。
- 解析 worker 数建议 ≈ GOMAXPROCS（8–16）：实测 1→8 worker 只快 2.1×，瓶颈是大分配速率下的 GC 与内存带宽，不要给 110 页各起一个解析 goroutine。
- Go 1.25 起 GOMAXPROCS 容器感知（按 cgroup CPU 限额），因此"单核/低配 VPS"场景会真实按 1 核算，第 4.5 节的结论在该类部署下成立。

**已被实测否掉，不要做**
- `antchfx/htmlquery`（分配是 goquery 的 4 倍，比 goquery 更慢）。
- 用纯 regexp 整页切块替代 DOM（实测最慢 3.2–8.2ms，尾延迟最差；Go 里不会崩，但语义脆。regexp 仍适合"正文内抽网盘链接/提取码"这类文本子任务）。
- `google/gumbo-parser`（2016 年停止维护，README 明确不建议使用）。
- 缓存/预编译 cascadia 选择器（实测只占 0.2%）。
- 连接池调优（HTTP/2 下只开 2 条 TCP）。
- ETag / If-None-Match（上游 `no-store` 且无验证器，RFC 9111 §4.3 意义上的条件请求不成立）。
- 为"带字面前缀的正则"额外加 `strings.Contains` 预筛（实测零收益，Go regexp 内部已有 literal prefix early reject）。
- 20 个 host 合并成一个大 alternation 正则（实测比现状慢 2.7×，比 20 次 `strings.Contains` 慢 110×）。
- `FindAllString` 换 `FindAllStringIndex`（更慢且更占内存）。
- 请求对冲 hedged requests（当前延迟方差≈0，前提不存在；只有观测到双峰后才对慢频道单次对冲）。
- 自研令牌桶限流（440 并发无任何限流反应）。

## 七、外部调研要点与来源

**Go 正则**
- regexp 官方文档示例注明 "Compile the expression once, usually at init time"；`staticcheck SA6000` 覆盖循环内 `regexp.Match` 一类问题；`go vet` 没有对应检查。
- `golang/go#63550`：给 regexp 增加编译缓存的提议**被关闭**——标准库不提供缓存，包级预编译是唯一正解。
- `golang/go#24411`：regexp 内部池争用曾导致 Prometheus 74k goroutine 中 15383 个卡在 `regexp.get`，Go 1.12 修复；当前版本并发使用无额外代价。
- `golang/go#13288`：`strings.Contains(strings.ToLower(s))` 7.8s vs `(?i)` 正则 21.7s。
- 手写扫描对照（同机实测）：取 `?pwd=` 正则 1096ns vs `strings.Index` 17.1ns（64×）；单行取"提取码：xxxx" 1263ns vs 95.7ns（13×）。

**t.me 抓取**
- 关键陷阱：搜索结果到底后页面**仍渲染 `before` 链接**，不能用"存在 before 链接"判断还有更多；可靠判据是"最小 message id 是否严格小于上一页"。搜索页单页上限 20 条。
- 无结果页含 `.tme_no_messages_found`；[RSSHub telegram 路由](https://github.com/DIYgod/RSSHub/blob/master/lib/routes/telegram/channel.ts) 用它区分"无匹配"与"抓取失败"，并记录了 t.me/s 把 `&` 改写成 `&amp;` 的历史 bug。
- [RSSHub](https://github.com/DIYgod/RSSHub) 使用 cheerio DOM 解析 + URL 级 TTL 缓存；注释指出部分频道在 `/s/` 路径不可用，需回退 Telegram API——**失败静默丢弃会丢真实数据**。
- [miniflux 配置](https://miniflux.app/docs/configuration.html)：`POLLING_PARSING_ERROR_LIMIT=3`（超限即停轮询）、`WORKER_POOL_SIZE=16`、`HTTP_CLIENT_TIMEOUT=20s`、按更新频率自适应调度。
- 官方限流文档只覆盖 MTProto 的 `420 FLOOD_WAIT_X`：https://core.telegram.org/api/errors ；t.me 网页抓取的限流策略无公开文档。
- [RFC 9113 §6.5.2](https://www.rfc-editor.org/rfc/rfc9113.html)：单个 HTTP/2 连接的并发流建议不少于 100（实测 t.me 行为值即为 100）。
- [RFC 9111 §4.3](https://www.rfc-editor.org/rfc/rfc9111.html)：条件请求需要验证器，本场景不存在。

**尾延迟与预算**
- [gRPC 请求对冲](https://grpc.io/docs/guides/request-hedging/)：用于削减长尾，但会放大后端负载，需配 throttling 与 server pushback。
- [SRE Book ch21](https://sre.google/sre-book/handling-overload/)：degraded responses、重试预算；[ch22](https://sre.google/sre-book/addressing-cascading-failures/)：deadline 传播、fail-fast、graceful degradation。
- [Solr `timeAllowed`](https://solr.apache.org/guide/solr/latest/query-guide/common-query-parameters.html) 配 `partialResults`；[Elasticsearch `allow_partial_search_results`](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-search.html) 默认为 true——两家都把"到点返回部分结果"作为默认语义。
- 《The Tail at Scale》（[ACM Queue](https://queue.acm.org/detail.cfm?id=2488748)）本次未能抓取全文（来源站点拦截），仅作方向引用。

**HTML 解析实现**
- [x/net/html 文档](https://pkg.go.dev/golang.org/x/net/html)：低层 API "performs fewer allocations and copies"；`Token()` 会复制 Data/Attr，`Text/TagName/TagAttr` 返回切片会随后续 Next 失效；`Raw()` 保证 token 对原始字节流构成无重叠无间隙分区（分块扫描的依据）。
- [goquery](https://github.com/PuerkitoBio/goquery)：官方唯一的性能建议是 2014-11-07 引入的 `*Matcher`（选择器编译一次复用）；`Find(selector)` 每次调用 `cascadia.Compile`（`traversal.go:23-25`、`type.go:166-172`），`Html()` = `html.Render` 重建子树 + `buf.String()` 二次拷贝（`property.go:97-113`），`Text()` 走 `bytes.Buffer`（`property.go:62-82`）。
- [htmlquery](https://github.com/antchfx/htmlquery)：内置 LRU 选择器缓存（README 自报 55.2ns vs 3162ns），但整体分配仍远高于 goquery。
- [CVE-2025-47911](https://api.osv.dev/v1/vulns/CVE-2025-47911) / [GO-2026-4440](https://pkg.go.dev/vuln/GO-2026-4440)：`x/net/html` 的 `html.Parse` 二次复杂度 DoS，修复版 0.45.0（已核实）。
- [Jeff Atwood: Parsing HTML the Cthulhu Way](https://blog.codinghorror.com/parsing-html-the-cthulhu-way/) 与 [SO #1732348](https://stackoverflow.com/questions/1732348/regex-match-open-tags-except-xhtml-self-contained-tags)：作者在"HTML 不是正则语言"之外明确反对"每个琐碎任务都上完整 parser"，关键区分是 parsing HTML 与 processing a few strings。
- [Cloudflare HTML 解析系列](https://blog.cloudflare.com/html-parsing-1/) / [lol-html](https://github.com/cloudflare/lol-html)：生产级选择是流式重写器（最小缓冲、受限内存）。
- 第三方独立实测（673 个真实站点）：[regex vs goquery vs net/html](https://edgecomet.com/blog/regex-vs-goquery-vs-net-html-a-performance-benchmark/)——单字段提取 regex 8µs vs DOM 1.59ms（约 200×），多字段 P50 regex 1.35ms vs goquery 1.80ms（仅差 22%），脚本清理 P99 regex 82.4ms vs net/html 16.1ms → "正则更快"只在**单字段、结构简单**时成立。
- [Russ Cox: RE2](https://swtch.com/~rsc/regexp/regexp1.html)、[容器感知 GOMAXPROCS](https://go.dev/blog/container-aware-gomaxprocs)、[Go 1.25 发布说明](https://go.dev/doc/go1.25)。

## 八、未验证项

- 生产代理出口的真实延迟分布：本报告用本地代理复刻，出口 IP 的共享程度与信誉无法代表生产环境。
- t.me 的长期速率限制与封禁策略：无任何公开文档，本轮 2000+ 次请求未触发。
- `?q=` 搜索翻页的深度上限：仅确认可回溯数百条历史。
- 生产环境（Linux + 多核容器）下的 GOMAXPROCS 与 GC 表现与 macOS 本机存在差异，第 4.5 节的单核结论需在目标环境复测（Go 1.25 起容器内按 cgroup 限额设定 GOMAXPROCS）。
- 解析基准的样本页多数是新闻类频道，**不含内联键盘按钮块**；键盘块结构按 Telegram widget 类名注入模拟，真实含按钮页面上"链接提取"一栏的耗时需实测复核。
- 解析类 benchmark 的绝对 ns/op 受本机热降频影响可达 ±40%，文档中跨 run 的数字只作量级参考，同 run 内的相对倍数才可靠。
- 未找到权威第三方对"tokenizer vs DOM 在 Telegram 预览页上的收益"的同场景量化对比，本项目的该组数字全部为本地实测。
