## 二、明确不做或暂缓的项

### 整页 DOM 换成手写分块扫描（暂缓）

实测整页解析 **14.8ms/页**（122–159KB、17–20 条消息），110 频道合计约 1.63s CPU。

但 pprof 显示解析路径的成本构成是：正则扫描 29.8%、`ExtractPassword` 24.0%、
DOM 构建 22.7%、cascadia 选择器 7.1%。分块扫描只能消掉 DOM 构建 + 选择器这约 30%，
**剩下的 54% 正则成本一分不动**。折算端到端约 2.4%（8 核）。

代价是 321 行语义复刻（标题分档、正文/键盘按钮链接合并、密码归属、去重规则），
回归风险与 2.4% 的收益不匹配。

**结论：不以"重构"名义重写这段。** 若将来单核部署导致 4 秒预算吃紧，再在有字段级等价测试的前提下做。

### 自动降级慢频道 / 慢插件（不做）

慢项只报告、不自动剔除。自动剔除会静默丢掉**仍在产出结果**的频道——
`yoyokuakeduanju` 耗时 3.7 秒但成功返回结果，剔除它就是拿数据完整性换延迟，
与"兜底数据要完整"的目标直接冲突。是否裁剪应由部署方按实测决定，因此只提供数据不下判断。

### 已被实测否掉的方案（不要重复尝试）

| 方案 | 实测结果 |
|---|---|
| 把 20 个域名合并成一个 alternation 正则 | 慢 2.7 倍 |
| 用 `strings.Contains` 做字面量前缀预筛 | 零收益 |
| 改用 `FindAllStringIndex` | 更慢、分配更多 |
| ETag / If-None-Match 条件请求 | 上游无 ETag/Last-Modified，结构上不可能 |
| 对冲请求（hedged request） | 方差≈0，无收益 |
| `antchfx/htmlquery` / `gumbo` | 分配 4 倍 / 已停止维护 |

## 七、两项排查结论（含一次自我纠错）

### `yingso`：确认是插件失效，已修复

站点在 2026-09 变更了混淆接口，插件三处同时失效，因此长期只能报
"获取接口配置失败"。证据链：

| 环节 | 插件原值 | 线上现值 |
|---|---|---|
| 配置接口 | `GET /test` | `GET /test1`（旧路径 Express 404） |
| 配置 XOR 密钥 | `12345678` | `672134612` |
| 取分享链接 | `POST /{v}/getKey` | `POST /{v}/getKey670I23762183` |

旁证：`yingso.fun` 证书 `notAfter=2026-09-24 01:59:59 GMT`，已过期；
前端 bundle 的 request 模块显示搜索与取链接协议本身未变。

修复后实测：单插件 0.43 秒返回 30 条，链接有效；端到端插件成功数 52/72 → 54/72。
实现按"新端点优先、旧端点兜底"成对尝试，站点再次变更时不至于整体失效。

### `u3c3`：**不是插件缺陷**，是我的测试环境问题

日志里 `u3c3` 耗时 10–12 秒，一度被当作慢插件。核查后推翻：

- `u3c3.com` 在本机经代理访问返回 `SSL_ERROR_SYSCALL`
- `nslookup u3c3.com` 返回 `127.0.0.1`（DNS 查询被本地代理拦截）
- 系统解析器的结果却是真实 Cloudflare 地址 `2606:4700:3035::ac43:a04e`
- 同期对照组 `yingso.fun` 也变成 `000`

即**本机代理当时无法访问 `u3c3.com`**，与同批次的其它站点一起失败。插件的
镜像回退逻辑本身按设计工作（先试主镜像、失败后切兜底镜像并记住）。

结论：**不改插件镜像配置**。这与第二节"3 秒预算"是同一类错误——把本机环境的
特殊条件当成通用缺陷去改代码。两次都是实测复核推翻了初判。

## 八、插件 HTTP 客户端碎片化：先测量，再改一处

`plugin/` 下 77 个文件、104 处自建 `&http.Client{}`，**没有任何插件使用共享客户端**
`util.GetHTTPClient()`。其中 52 处显式设置 `Transport`，31 处在函数内每次新建。

排查中先纠正了一个自己的误判：`Transport` 为 nil 的 client 会用
`http.DefaultTransport`，**连接池仍是共享的**，所以"每次新建 client 就丢连接复用"
并不成立。真正的问题是 `DefaultTransport` 每主机只保留 **2** 条空闲连接。

同时发现插件框架自己给的客户端也是 `&http.Client{Timeout: ...}`（Transport 为 nil），
所以**之前为共享客户端加的调优（每主机 110、保活 600s）对插件路径完全没有作用**——
插件路径和 TG 频道路径走的是两套连接池。

### 测量（复现插件真实配置，5 轮 × 8 并发，同一主机）

| 配置 | 新建连接 | 每轮新建 |
|---|---|---|
| 调优前 `DefaultTransport`（idle/主机=2） | 32 条 | 6.4 |
| 调优后（idle/主机=20，保活 90s） | 8 条 | 1.6 |

即并发突发结束后多余连接不再被立刻关闭，下一轮搜索省掉重新握手。连接数下降 75%；
本机 TLS 握手便宜，耗时只差 8%（374.9ms → 364.0ms），真实网络每次握手 100-300ms。

**测量过程本身也修了一个错**：第一版基准没读 body 就 `Close`，连接无法复用，
导致"调优前后都是 8 条/轮"的假结论。Go 需要读到 EOF 才归还连接到空闲池。

### 实现：只改一处

在 `util.TuneDefaultTransport()` 中调优 `http.DefaultTransport` 的连接池，由
`InitHTTPClient()` 在 `config.Init()` 之后调用。这样框架客户端与 77 个文件里
Transport 为 nil 的自建客户端**全部**被覆盖，不需要动那 77 个文件。

（本节当时的"刻意不动 Proxy"结论是**错的**，已在第十一节更正——见下文。）

### 验证

- `util/http_util_test.go`：调优生效、配置覆盖生效
- 启动日志可观测：`[HTTP] 已调优 DefaultTransport：每主机空闲连接 110，保活 10m0s，代理=...`
- 端到端：yingso 单独搜索 1.97s / 1.29s（各 30 条），功能无回归

### 未做（有据）

- **不给 52 处自定义 `Transport` 的插件统一换连接池**：它们各有站点特性（TLS 指纹、
  超时、代理），统一替换需要逐个验证，收益重叠且风险高于收益。

## 九、refresh 失败路径：插件结果凭空消失

### 现象

`refresh=true` 时 gying 结果消失。

### 根因（不是 refresh 机制本身）

refresh 机制是对的——它确实跳过了插件缓存。问题在失败路径上有两层吞错：

1. gying 的 `executeSearchTasks` 把每个用户的错误都吞掉，抓取失败时返回**空切片且不带 error**，
   插件以"成功、0 条"上报。而 refresh 恰好跳过缓存，两者叠加就表现为"一刷新结果就没了"。
2. 框架层 `AsyncSearch` 在 `err != nil` 时直接返回错误，调用方 `service.searchPlugins`
   在 `err != nil` 分支 `continue` **丢弃结果**。所以任何插件抓取失败都会从结果里消失，
   不只是 gying。

### 改动

- gying：`executeSearchTasks` 返回 `(results, error)`，区分"全部抓取失败"（`succeeded==0`
  且有错误）与"抓取成功但确实无匹配"——后者是合法空结果，不能当失败上报。
- gying：刷新或没有可用账号时，若已有缓存则回退缓存并打印日志；无缓存可回退时如实返回错误。
- 框架：`AsyncSearch` 与 `AsyncSearchWithResult` 的错误分支回退缓存，与超时路径
  `partial()` 的既有语义（"响应超时，返回部分缓存"）对齐。因调用方会丢弃 `err != nil`
  的结果，这里返回 `nil` error 并打印明确日志，兼顾数据可用性与可观测性。

### 验证

- `plugin/gying/gying_refresh_test.go`：刷新回退缓存 / 非刷新缓存命中 / 无缓存时不报错
- `plugin/plugin_fallback_test.go`：有缓存则回退、无缓存则如实报错
- 端到端：gying 的失败由"静默 0 条"变为可追溯的 `网络错误 x1`，附带 `Get "...": EOF` 原因

## 十一、代理解析统一（含对第八节结论的更正）

### 先更正一个错误结论

第八节曾写："共享客户端的 `applyProxy("")` 什么都不做，**它只认 `config.ProxyURL`，
不认 `HTTP_PROXY` 环境变量**，所以不能拿给插件用"。**这个结论是错的。**

`config.getProxyURL()`（config.go:220）本身就是多来源解析：

```
PROXY → HTTPS_PROXY/https_proxy → HTTP_PROXY/http_proxy → ALL_PROXY/all_proxy
```

也就是说 `config.ProxyURL` **已经合并了这些环境变量**，共享客户端一直是认环境变量的。
当时只看到 `applyProxy("")` 提前 return，就跳过了"config 已经把环境变量填进来"这一步，
把一个不存在的阻塞当成了结论。顺带纠正参数名：环境变量是 **`PROXY`**（README 第 99 行），
`ProxyURL` 只是 Go 结构体字段名，不是可配置的参数名。

### 真正的缺口在反方向

核实 `httpproxy`（`ProxyFromEnvironment` 的实现）后确认，它只读
`HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY`，**不读 `PROXY`，也不读 `ALL_PROXY`**：

| 变量 | 共享客户端（TG 频道路径） | `ProxyFromEnvironment`（插件路径） |
|---|---|---|
| `PROXY` | ✅ 读（README 主推参数） | ❌ **不读** |
| `HTTPS_PROXY` / `HTTP_PROXY` | ✅ 读 | ✅ 读 |
| `ALL_PROXY` | ✅ 读 | ❌ **不读** |
| `NO_PROXY` | ❌ 不处理 | ✅ 处理 |

插件路径全部走 `http.DefaultTransport`，因此**只配置 `PROXY`（或只配置 `ALL_PROXY`）时，
所有插件都会静默退回直连**——而 TG 频道照常走代理。这是个真实的配置陷阱：
按 README 最推荐的 `PROXY=...` 配置，恰好是插件失效的那种配法。

### 改动

1. 新增 `config.NoProxy`（读取 `NO_PROXY`/`no_proxy`），沿用项目"环境变量集中在 config"的约定。
2. `util.BuildProxyFunc(rawProxyURL, noProxy)` 统一代理解析：显式配置的代理优先并
   **按 `NO_PROXY` 放行直连**（`http.ProxyURL` 不做这件事，改用 `x/net/http/httpproxy` 的
   `Config.ProxyFunc()`）；未配置任何代理时交回 `ProxyFromEnvironment`，保持标准语义。
3. `TuneDefaultTransport()` 一并接线代理，插件路径与频道路径从此同一套解析。
4. 顺带去掉 `x/net/proxy` 的 socks5 自定义 `DialContext`：`Transport.Proxy` 原生支持
   `socks5`（含账号密码、本地解析域名），`socks5h` 归一化为 `socks5`。这样 TCP 拨号
   参数不再被代理分支覆盖。

### 验证（对照组自证）

`util/http_util_test.go` 新增 7 项用例。其中 `TestPluginPathProxyWiringLive` 用
`google.com` 作判别（本机直连不通、经代理可通），且**自带对照组**：

- 对照组（把 `Proxy` 还原为修复前的 `ProxyFromEnvironment`，只设 `PROXY`）→
  `context deadline exceeded`，确认修复前确实退回直连
- 修复后 → `200`

对照组失败才继续断言，若本机直连可达则直接 skip，避免用例失去判别力还装作通过。

## 十二、插件客户端超时被构造阶段冻结（配置静默失效）

### 问题

插件是在**各自包的 `init()`** 里构造的（`RegisterGlobalPlugin(NewYingsoPlugin())`），
而 `config.Init()` 在 `main.go:120` 的 `initApp()` 里才执行。也就是说构造那一刻
`config.AppConfig` 恒为 `nil`，构造函数里 `if config.AppConfig != nil` 的分支永远走不到。

后果有三个配置项被静默忽略：

| 配置项 | 期望 | 实际（修复前） |
|---|---|---|
| `ASYNC_RESPONSE_TIMEOUT` | 决定短超时客户端 | 恒为硬编码 4s |
| `PLUGIN_TIMEOUT` | 决定长超时客户端 | 恒为硬编码 30s |
| `ASYNC_CACHE_TTL_HOURS` | 决定内存缓存有效期 | 恒为硬编码 1h |

注意 `AsyncSearch` 里的 **select 超时**是在请求时读配置的，所以配小值（如 1s）看起来
"生效"；但配大值（如 12s）时，select 会等 12s，而底层客户端早在 4s 就报错——表现为
"超时配置调大了却没有任何效果"。Dockerfile 恰好把 `ASYNC_RESPONSE_TIMEOUT` 设为 4
（等于硬编码默认值），所以默认部署完全看不出来。

### 改动

超时与缓存有效期改为**调用时解析**，不再在构造阶段读取：

- 新增 `pluginClientTimeouts()` 与 `(*BaseAsyncPlugin).getCacheTTL()`
- `client` / `backgroundClient` 改为懒创建（各自一个 `sync.Once`），首次取用时按
  当时的配置构造；`GetClient()` 的对外签名不变
- `p.cacheTTL` 的 9 处读取改为 `p.getCacheTTL()`
- 首次解析时打一行 `[PLUGIN] 插件客户端超时按当前配置解析：响应 X，处理 Y`，
  让"配置到底生不生效"可以被直接看到，而不是靠猜

### 验证

- `plugin/plugin_config_lazy_test.go`：先构造、后配置 → 取到配置值；无配置 → 退回
  硬编码默认值；重复取用返回同一实例（不丢连接复用）
- 运行时：`ASYNC_RESPONSE_TIMEOUT=11 PLUGIN_TIMEOUT=45` 启动，日志输出
  `响应 11s，处理 45s`，搜索 30 条无回归

## 十三、插件源全量审计（75 个）与失败原因可观测性

### 方法与判别原则

新增门控审计 `main_plugin_audit_test.go`（默认跳过，`AUDIT_PLUGIN_SOURCES=1` 才跑）：
逐个调用已注册插件并按 `refresh` 取一轮，等 35 秒让后台补齐完成后再复核一轮，
两轮都没结果才算"空"。

判别原则（这条比结论本身重要）：

- **只有"解析/结构类"错误**才能断定插件自身失效——这类证据与本机网络无关。
- **403 / 444 / EOF / connection reset 一律不可判定**：它们高度可能是代理出口 IP
  被拒，本机环境不足以区分"站点封了我的出口"与"插件坏了"。
- 任何结论都不从本机网络推广到部署环境（`u3c3`、`gying` 两次教训）。

### 结果

75 个插件：健康 29、抓取失败 20、两轮后仍空 26。

**可判定为站点/插件层面问题（环境无关）**

| 插件 | 现象 | 判断 |
|---|---|---|
| `cldi` | `重试 3 次后仍然失败: %!w(<nil>)` | **代码缺陷**，已修，见下 |
| `clxiong` | 期望 302 重定向，实得 400 | 站点协议变更 |
| `xb6v` | 未找到搜索结果页重定向信息 | 页面结构变更 |
| `erxiao` | `lookup www.2xiaopan.top: no such host` | 域名已不存在 |
| `sousou` | `page 3, type BDY: 567` | 第 3 页失败，前两页可用 |
| `buerchen` | `CHALLENGE_REQUIRED code=42901` | 站点加挑战（先前已记录） |

**不可判定（需在真实部署环境复核，不能据此裁剪）**

- 403：`dyyj` `dyyjpro` `libvio` `miosou` `quarktv` `zlxapp`
- 444：`dy4k` `yunsou`
- EOF：`hunhepan` `leso` `rrbt` `u3c3` `xdpan`
- connection reset：`thepiratebay`

**两轮后仍空的 26 个**里，有一组耗时精确落在 **4.000s / 4.004s / 4.027s**：
`duanjuw` `duoduo` `feikuai` `kpkuang` `pan365` `quark4k` `quarksoo` `sopanya`
`zhizhen`。这正好是 `ASYNC_RESPONSE_TIMEOUT` 的默认值，说明它们是**卡在响应超时
返回了部分空结果**，而不是"真没有匹配内容"。这一组值得单独跟进，但性质是"慢"，
不是"死"。

### 已修：失败原因被丢弃（41 个文件）

审计里 `cldi` 报出 `%!w(<nil>)`，顺着查到一段被复制到 41 个插件的重试循环：

```go
resp, err := client.Do(reqClone)
if err == nil && resp.StatusCode == 200 {
    return resp, nil
}
if resp != nil {
    resp.Body.Close()
}
lastErr = err        // err == nil 时把 lastErr 清空
```

服务器返回非 200 时 `client.Do` 的 `err` 为 `nil`，于是 `lastErr` 被置空，重试三次后
只能报 `%!w(<nil>)` 或干脆只剩"重试 N 次后仍然失败"，**真实状态码彻底丢失**。
这与前几批"让失败可观测"是同一条主线：没有状态码就无法区分反爬、改版与网络抖动。

改动：`err == nil && resp != nil` 时补一个 `err = fmt.Errorf("HTTP 状态码 %d", status)`，
只在原处加信息，不改重试与退避逻辑。41 个文件统一处理，另 5 个经人工核对**不是同一
问题**（`kpkuang`/`hjzhencai`/`miosou` 的赋值在 `err != nil` 分支内；`clmao`/`wuji`
是"不看状态码就返回"，属行为差异，不在此次范围）。

验证：修复后 `cldi` 的报错变为
`[cldi] 搜索第一页失败: ... 重试 3 次后仍然失败: HTTP 状态码 4xx`。

### 测量后记录、未改动

- **19 处插件手写 `Transport: &http.Transport{...}`，没有一处设置 `Proxy`**：
  这些插件完全无视代理配置（包括刚统一的 `PROXY`）。改动需要逐个保留其
  TLS/超时特性，且审计显示这些插件的真实问题在别处，故记录不批量改。
  将来要动，正确做法是 `http.DefaultTransport.(*http.Transport).Clone()`
  再覆盖各自的自定义字段（继承代理与连接池）。
- **`qqpd` 在二维码登录路径内联了 4 个 `&http.Transport{}`**：既丢连接池
  （零值 Transport 退回默认每主机 2 条）也没有代理，且带 `InsecureSkipVerify`。
  属登录链路，非搜索热路径。
- **"52 处自定义 Transport"的旧说法要修正**：真正"每次调用新建独立连接池"的
  只有 `qqpd` 的 4 处（`panyq` 经核对是复用 `client.Transport`，误报）；
  其余 48 处只在构造时建一次，属正常。

## 十四、慢插件是"慢"不是"死"（实证），以及"成功但零产出"的盲区

### 先做实验，再决定要不要改

第十三节里那一组耗时精确落在 4.000s 的插件（`duanjuw` `duoduo` `feikuai`
`kpkuang` `pan365` `quark4k` `quarksoo` `sopanya` `zhizhen`），先用同一批插件、
同一个关键词对比不同预算：

| `ASYNC_RESPONSE_TIMEOUT` | 响应耗时 | 返回条数 |
|---|---|---|
| 4（默认） | 4.01s | **0** |
| 15 | 13.7s | **55** |

**结论：它们是慢，不是死。** 给足预算就有 55 条，默认窗口下一条都拿不到。

紧接着验证后台补齐是否真的把这些结果送达：4 秒窗口下第一次搜索返回 0 条，
等 25 秒后再搜（不刷新）——**0.005s 命中缓存，55 条**。

也就是说设计意图是成立的：快路径按 4 秒返回，慢插件的内容随后由后台补齐进入缓存。
**这 9 个插件不需要改动。**

### 但暴露了一个真盲区：`complete()` 不看出没出结果

同一批日志里写着"慢项 `quark4k` 耗时 4000ms **成功**"，汇总写着"成功 7/9"，
而用户这一轮实际拿到 0 条。两类完全不同的情况被同一个"成功"混在一起。

更严重的是缓存判定。原 `complete()` 只要求"没有超时也没有失败"：

```go
func (o *batchSearchOutcome) complete() bool { return len(o.missing) == 0 && o.failed == 0 }
```

于是"全部成功但零产出"会被判为**完整结果**，按完整 TTL（默认 60 分钟）缓存一整个
周期；而 `shouldBackfill` 又因 `timedOut() == 0` 不触发补齐。空结果就这样被锁住一小时。

这与第一批消掉的债（"插件路径是 TG 缓存污染的同源第二入口"）是同一类问题，
只是触发条件从"失败"换成了"成功但没内容"。

### 改动

- 新增 `observeYield(id, contributed)`：记录每个任务本轮真正贡献的可用结果条数
- 新增 `requireYieldTracking()`：**只由插件路径开启**。插件路径下 4 秒窗口返回空是
  常态；频道路径不开启——频道确实可能没有匹配内容，那种空结果应当照常缓存。
  若把频道路径也纳入，会让"无匹配"的正常批次每轮都重新抓取一遍。
- `cacheTTL`：插件路径下整批零产出直接不写缓存
- `logSummary`：新增"本轮零产出 N"计数与明细名单，并让它单独也能触发输出
  （原来只有失败或超时才输出，全空批次反而一声不响）

### 验证

- `service/batch_search_test.go` 新增 4 个子用例：插件路径整批零产出不写缓存、
  有任意产出即恢复正常判定、频道路径零产出仍照常缓存、零产出不改变失败/超时判定
- 实测冷启动（全新缓存目录）：第一次搜索 4.01s / 0 条，日志输出

```
[searchPlugins] 仙逆：成功 8/9，失败 1，超时未完成 0，本轮零产出 8；失败原因 网络错误×1（示例: ...）
[searchPlugins] 仙逆：本轮零产出（内容需靠后台补齐）: pan365 quark4k feikuai duoduo duanjuw zhizhen kpkuang quarksoo
```

修复前这一行只有"成功 8/9"，完全看不出用户其实一条都没拿到。
