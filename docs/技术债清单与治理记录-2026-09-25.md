# 技术债清单与治理记录（2026-09-25）

承接 [TG 快速兜底搜索：性能分析、技术债与优化方案](./TG快速兜底搜索性能分析与优化-2026-09-24.md)。
本文记录该轮优化之后的债务清偿工作：消除了什么、依据是什么、哪些明确不做。

所有结论都来自本机实测，未实测的部分单独标注为"未验证"。

## 一、本轮消除的债

| # | 问题 | 处置 | 证据 |
|---|---|---|---|
| 1 | **插件路径是 TG 缓存污染的同源第二入口**：`searchPlugins` 同样无条件写 60 分钟 TTL，把一次抖动的残缺结果锁住整个缓存周期 | 抽出 `service/batch_search.go` 作为两条路径共用的完整度判定：失败与超时分开统计、TTL 按完整度分流、后台补齐 | 单测 11 个分支；插件路径端到端结果与改动前一致（739/745 → 736/743，属正常波动） |
| 2 | **上一轮我引入的过度收紧**：`TG_CHANNEL_TIMEOUT_SECONDS` 默认 3 秒，把聚合窗口压到单频道预算（4 秒）之下 | 默认值改为 `0` = 跟随单频道请求超时，即项目原有行为；只有实测确认不丢结果才收紧 | `searchChannelWithContext` 每请求自带 4 秒上限，批次自然在约 4 秒返回 |
| 3 | 123 处正则写在函数体内，每次调用重新解析模式 | AST 工具批量提取到包级（40 个文件）；同文件相同字面量共享一个变量 | 函数内残留归零；`ExtractPassword` 单次 23.5µs → 6.7µs |
| 4 | `plugin/dyyj` 两处按 pattern 字符串在循环里 `MustCompile` | 改为包级预编译切片 | 编译 + 单测通过 |
| 5 | `ParseSearchResults` 每条消息把正文序列化成 HTML、再正则换行、再剥标签、再解实体，而结果只是同一棵 DOM 的文本投影 | 新增 `messageTextWithBreaks` 直接从 DOM 拼出带换行文本 | **4 个真实页面 77 条消息，正文与标题输出零差异**；同批消息提取 458µs → 26.7µs（17×） |
| 6 | `nextPageParam` 声明后从未赋值，恒为空串（翻页功能从未实现） | 移除死变量，保留原签名兼容 | 残留引用 0 |
| 7 | 0 条结果无法区分"频道确实没有匹配内容"与"t.me 改版导致解析失效"，站点一改版就静默归零 | 新增 `PageParseStatus` 三态 + `ParseSearchResultsWithStatus` | 三态用例全通过，含真实无结果页结构 |
| 8 | 批次失败只汇总成一个数字，不知道是限流还是改版，也不知道谁拖慢了整批 | `httpStatusError` 类型化状态码 + `failureClass` 归类 + 慢项 Top5 | 日志直接定位出下面第四节的三项具体债务 |

### 第 7 项的一处自我纠正

"结构失效"最初用 `len(results) == 0` 判定，实测立刻误报了 5 个频道。核查后发现
`Lsp115`、`wpzyk`、`MCPH03` 都是**消息结构完好、只是整条不含受支持的网盘链接**
（页面里 0 个网盘链接、0 个 magnet），0 条结果是正确的。

改为用"识别成功的消息块数"判定，并补了误报回归用例。**这个误报是实测发现的，不是推理发现的。**

## 二、明确不做或暂缓的项

### 整页 DOM 换成手写分块扫描（暂缓）

实测整页解析 **14.8ms/页**（122–159KB、17–20 条消息），110 频道合计约 1.63s CPU。

但 pprof 显示解析路径的成本构成是：正则扫描 29.8%、`ExtractPassword` 24.0%、
DOM 构建 22.7%、cascadia 选择器 7.1%。分块扫描只能消掉 DOM 构建 + 选择器这约 30%，
**剩下的 54% 正则成本一分不动**。折算端到端约 2.4%（8 核）。

代价是 321 行语义复刻（标题分档、正文/键盘按钮链接合并、密码归属、去重规则），
回归风险与 2.4% 的收益不匹配。

**结论：不以"重构"名义重写这段。** 若将来单核部署导致 4 秒预算吃紧，再在有字段级等价测试的前提下做。

### 自动降级慢频道 / 慢插件（不做）

慢项只报告、不自动剔除。自动剔除会静默丢掉**仍在产出结果**的频道——
`yoyokuakeduanju` 耗时 3.7 秒但成功返回结果，剔除它就是拿数据完整性换延迟，
与"兜底数据要完整"的目标直接冲突。是否裁剪应由部署方按实测决定，因此只提供数据不下判断。

### 已被实测否掉的方案（不要重复尝试）

| 方案 | 实测结果 |
|---|---|
| 把 20 个域名合并成一个 alternation 正则 | 慢 2.7 倍 |
| 用 `strings.Contains` 做字面量前缀预筛 | 零收益 |
| 改用 `FindAllStringIndex` | 更慢、分配更多 |
| ETag / If-None-Match 条件请求 | 上游无 ETag/Last-Modified，结构上不可能 |
| 对冲请求（hedged request） | 方差≈0，无收益 |
| `antchfx/htmlquery` / `gumbo` | 分配 4 倍 / 已停止维护 |

## 三、新增配置项

全部默认值都**不改变项目原有行为**，只在需要时收紧或放开。

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `TG_CHANNEL_TIMEOUT_SECONDS` | `0`（跟随单频道超时） | 频道批收集窗口 |
| `TG_CHANNEL_REQUEST_TIMEOUT_SECONDS` | `4` | 单个频道请求超时 |
| `TG_RESPONSE_MAX_BYTES` | `2097152` | 单频道响应体上限 |
| `TG_BACKFILL_ENABLED` | `true` | 超时频道后台补齐 |
| `CACHE_PARTIAL_TTL_MINUTES` | `3` | 结果不完整时的缓存有效期 |
| `PLUGIN_BATCH_TIMEOUT_SECONDS` | `0`（沿用 `PLUGIN_TIMEOUT`） | 插件批收集窗口 |
| `PLUGIN_BACKFILL_ENABLED` | `true` | 超时插件后台补齐 |
| `UPSTREAM_IDLE_CONN_TIMEOUT_SECONDS` | `600` | 上游空闲连接保活 |
| `UPSTREAM_MAX_IDLE_CONNS_PER_HOST` | `110` | 每主机空闲连接数 |

## 五、验证方法

**隔离 A/B**：两个实例同时挂同一个上游代理会互相干扰。曾因此得到"优化后慢一倍"的
错误结论（12.1s vs 6.1s），隔离后两版耗时一致（`src=tg` 4.22/2.16s vs 4.33/2.17s，
`src=plugin` 13.30/13.93s vs 13.26/13.67s）。**并发环境下的对比数字一律不可信。**

**真实样本等价性**：改写解析逻辑时，用 4 个真实页面（`page_*.html`）复刻旧实现逐条比对，
77 条消息正文与标题零差异，而非只靠构造用例。

**契约测试**：`util/parser_contract_test.go` 锁定正文拼装、标题分档、解析三态；
`service/batch_search_test.go` 锁定缓存分流、补齐判定、失败归类、慢项排序。
标题用例走完整链路（HTML → DOM → 正文 → 标题），签名或实现替换都无法绕过。
