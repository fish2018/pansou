## 二、明确不做或暂缓的项

### 整页 DOM 换成手写分块扫描（暂缓）

实测整页解析 **14.8ms/页**（122–159KB、17–20 条消息），110 频道合计约 1.63s CPU。

但 pprof 显示解析路径的成本构成是：正则扫描 29.8%、`ExtractPassword` 24.0%、
DOM 构建 22.7%、cascadia 选择器 7.1%。分块扫描只能消掉 DOM 构建 + 选择器这约 30%，
**剩下的 54% 正则成本一分不动**。折算端到端约 2.4%（8 核）。

代价是 321 行语义复刻（标题分档、正文/键盘按钮链接合并、密码归属、去重规则），
回归风险与 2.4% 的收益不匹配。

**结论：不以"重构"名义重写这段。** 若将来单核部署导致 4 秒预算吃紧，再在有字段级等价测试的前提下做。

### 自动降级慢频道 / 慢插件（不做）

慢项只报告、不自动剔除。自动剔除会静默丢掉**仍在产出结果**的频道——
`yoyokuakeduanju` 耗时 3.7 秒但成功返回结果，剔除它就是拿数据完整性换延迟，
与"兜底数据要完整"的目标直接冲突。是否裁剪应由部署方按实测决定，因此只提供数据不下判断。

### 已被实测否掉的方案（不要重复尝试）

| 方案 | 实测结果 |
|---|---|
| 把 20 个域名合并成一个 alternation 正则 | 慢 2.7 倍 |
| 用 `strings.Contains` 做字面量前缀预筛 | 零收益 |
| 改用 `FindAllStringIndex` | 更慢、分配更多 |
| ETag / If-None-Match 条件请求 | 上游无 ETag/Last-Modified，结构上不可能 |
| 对冲请求（hedged request） | 方差≈0，无收益 |
| `antchfx/htmlquery` / `gumbo` | 分配 4 倍 / 已停止维护 |

## 七、两项排查结论（含一次自我纠错）

### `yingso`：确认是插件失效，已修复

站点在 2026-09 变更了混淆接口，插件三处同时失效，因此长期只能报
"获取接口配置失败"。证据链：

| 环节 | 插件原值 | 线上现值 |
|---|---|---|
| 配置接口 | `GET /test` | `GET /test1`（旧路径 Express 404） |
| 配置 XOR 密钥 | `12345678` | `672134612` |
| 取分享链接 | `POST /{v}/getKey` | `POST /{v}/getKey670I23762183` |

旁证：`yingso.fun` 证书 `notAfter=2026-09-24 01:59:59 GMT`，已过期；
前端 bundle 的 request 模块显示搜索与取链接协议本身未变。

修复后实测：单插件 0.43 秒返回 30 条，链接有效；端到端插件成功数 52/72 → 54/72。
实现按"新端点优先、旧端点兜底"成对尝试，站点再次变更时不至于整体失效。

### `u3c3`：**不是插件缺陷**，是我的测试环境问题

日志里 `u3c3` 耗时 10–12 秒，一度被当作慢插件。核查后推翻：

- `u3c3.com` 在本机经代理访问返回 `SSL_ERROR_SYSCALL`
- `nslookup u3c3.com` 返回 `127.0.0.1`（DNS 查询被本地代理拦截）
- 系统解析器的结果却是真实 Cloudflare 地址 `2606:4700:3035::ac43:a04e`
- 同期对照组 `yingso.fun` 也变成 `000`

即**本机代理当时无法访问 `u3c3.com`**，与同批次的其它站点一起失败。插件的
镜像回退逻辑本身按设计工作（先试主镜像、失败后切兜底镜像并记住）。

结论：**不改插件镜像配置**。这与第二节"3 秒预算"是同一类错误——把本机环境的
特殊条件当成通用缺陷去改代码。两次都是实测复核推翻了初判。

## 八、插件 HTTP 客户端碎片化：先测量，再改一处

`plugin/` 下 77 个文件、104 处自建 `&http.Client{}`，**没有任何插件使用共享客户端**
`util.GetHTTPClient()`。其中 52 处显式设置 `Transport`，31 处在函数内每次新建。

排查中先纠正了一个自己的误判：`Transport` 为 nil 的 client 会用
`http.DefaultTransport`，**连接池仍是共享的**，所以"每次新建 client 就丢连接复用"
并不成立。真正的问题是 `DefaultTransport` 每主机只保留 **2** 条空闲连接。

同时发现插件框架自己给的客户端也是 `&http.Client{Timeout: ...}`（Transport 为 nil），
所以**之前为共享客户端加的调优（每主机 110、保活 600s）对插件路径完全没有作用**——
插件路径和 TG 频道路径走的是两套连接池。

### 测量（复现插件真实配置，5 轮 × 8 并发，同一主机）

| 配置 | 新建连接 | 每轮新建 |
|---|---|---|
| 调优前 `DefaultTransport`（idle/主机=2） | 32 条 | 6.4 |
| 调优后（idle/主机=20，保活 90s） | 8 条 | 1.6 |

即并发突发结束后多余连接不再被立刻关闭，下一轮搜索省掉重新握手。连接数下降 75%；
本机 TLS 握手便宜，耗时只差 8%（374.9ms → 364.0ms），真实网络每次握手 100-300ms。

**测量过程本身也修了一个错**：第一版基准没读 body 就 `Close`，连接无法复用，
导致"调优前后都是 8 条/轮"的假结论。Go 需要读到 EOF 才归还连接到空闲池。

### 实现：只改一处

在 `util.TuneDefaultTransport()` 中调优 `http.DefaultTransport` 的连接池，由
`InitHTTPClient()` 在 `config.Init()` 之后调用。这样框架客户端与 77 个文件里
Transport 为 nil 的自建客户端**全部**被覆盖，不需要动那 77 个文件。

（本节当时的"刻意不动 Proxy"结论是**错的**，已在第十一节更正——见下文。）

### 验证

- `util/http_util_test.go`：调优生效、配置覆盖生效
- 启动日志可观测：`[HTTP] 已调优 DefaultTransport：每主机空闲连接 110，保活 10m0s，代理=...`
- 端到端：yingso 单独搜索 1.97s / 1.29s（各 30 条），功能无回归

### 未做（有据）

- **不给 52 处自定义 `Transport` 的插件统一换连接池**：它们各有站点特性（TLS 指纹、
  超时、代理），统一替换需要逐个验证，收益重叠且风险高于收益。

## 九、refresh 失败路径：插件结果凭空消失

### 现象

`refresh=true` 时 gying 结果消失。

### 根因（不是 refresh 机制本身）

refresh 机制是对的——它确实跳过了插件缓存。问题在失败路径上有两层吞错：

1. gying 的 `executeSearchTasks` 把每个用户的错误都吞掉，抓取失败时返回**空切片且不带 error**，
   插件以"成功、0 条"上报。而 refresh 恰好跳过缓存，两者叠加就表现为"一刷新结果就没了"。
2. 框架层 `AsyncSearch` 在 `err != nil` 时直接返回错误，调用方 `service.searchPlugins`
   在 `err != nil` 分支 `continue` **丢弃结果**。所以任何插件抓取失败都会从结果里消失，
   不只是 gying。

### 改动

- gying：`executeSearchTasks` 返回 `(results, error)`，区分"全部抓取失败"（`succeeded==0`
  且有错误）与"抓取成功但确实无匹配"——后者是合法空结果，不能当失败上报。
- gying：刷新或没有可用账号时，若已有缓存则回退缓存并打印日志；无缓存可回退时如实返回错误。
- 框架：`AsyncSearch` 与 `AsyncSearchWithResult` 的错误分支回退缓存，与超时路径
  `partial()` 的既有语义（"响应超时，返回部分缓存"）对齐。因调用方会丢弃 `err != nil`
  的结果，这里返回 `nil` error 并打印明确日志，兼顾数据可用性与可观测性。

### 验证

- `plugin/gying/gying_refresh_test.go`：刷新回退缓存 / 非刷新缓存命中 / 无缓存时不报错
- `plugin/plugin_fallback_test.go`：有缓存则回退、无缓存则如实报错
- 端到端：gying 的失败由"静默 0 条"变为可追溯的 `网络错误 x1`，附带 `Get "...": EOF` 原因

## 十一、代理解析统一（含对第八节结论的更正）

### 先更正一个错误结论

第八节曾写："共享客户端的 `applyProxy("")` 什么都不做，**它只认 `config.ProxyURL`，
不认 `HTTP_PROXY` 环境变量**，所以不能拿给插件用"。**这个结论是错的。**

`config.getProxyURL()`（config.go:220）本身就是多来源解析：

```
PROXY → HTTPS_PROXY/https_proxy → HTTP_PROXY/http_proxy → ALL_PROXY/all_proxy
```

也就是说 `config.ProxyURL` **已经合并了这些环境变量**，共享客户端一直是认环境变量的。
当时只看到 `applyProxy("")` 提前 return，就跳过了"config 已经把环境变量填进来"这一步，
把一个不存在的阻塞当成了结论。顺带纠正参数名：环境变量是 **`PROXY`**（README 第 99 行），
`ProxyURL` 只是 Go 结构体字段名，不是可配置的参数名。

### 真正的缺口在反方向

核实 `httpproxy`（`ProxyFromEnvironment` 的实现）后确认，它只读
`HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY`，**不读 `PROXY`，也不读 `ALL_PROXY`**：

| 变量 | 共享客户端（TG 频道路径） | `ProxyFromEnvironment`（插件路径） |
|---|---|---|
| `PROXY` | ✅ 读（README 主推参数） | ❌ **不读** |
| `HTTPS_PROXY` / `HTTP_PROXY` | ✅ 读 | ✅ 读 |
| `ALL_PROXY` | ✅ 读 | ❌ **不读** |
| `NO_PROXY` | ❌ 不处理 | ✅ 处理 |

插件路径全部走 `http.DefaultTransport`，因此**只配置 `PROXY`（或只配置 `ALL_PROXY`）时，
所有插件都会静默退回直连**——而 TG 频道照常走代理。这是个真实的配置陷阱：
按 README 最推荐的 `PROXY=...` 配置，恰好是插件失效的那种配法。

### 改动

1. 新增 `config.NoProxy`（读取 `NO_PROXY`/`no_proxy`），沿用项目"环境变量集中在 config"的约定。
2. `util.BuildProxyFunc(rawProxyURL, noProxy)` 统一代理解析：显式配置的代理优先并
   **按 `NO_PROXY` 放行直连**（`http.ProxyURL` 不做这件事，改用 `x/net/http/httpproxy` 的
   `Config.ProxyFunc()`）；未配置任何代理时交回 `ProxyFromEnvironment`，保持标准语义。
3. `TuneDefaultTransport()` 一并接线代理，插件路径与频道路径从此同一套解析。
4. 顺带去掉 `x/net/proxy` 的 socks5 自定义 `DialContext`：`Transport.Proxy` 原生支持
   `socks5`（含账号密码、本地解析域名），`socks5h` 归一化为 `socks5`。这样 TCP 拨号
   参数不再被代理分支覆盖。

### 验证（对照组自证）

`util/http_util_test.go` 新增 7 项用例。其中 `TestPluginPathProxyWiringLive` 用
`google.com` 作判别（本机直连不通、经代理可通），且**自带对照组**：

- 对照组（把 `Proxy` 还原为修复前的 `ProxyFromEnvironment`，只设 `PROXY`）→

- 修复后 → `200`

## 十二、插件客户端超时被构造阶段冻结（配置静默失效）

### 问题

插件是在**各自包的 `init()`** 里构造的（`RegisterGlobalPlugin(NewYingsoPlugin())`），
而 `config.Init()` 在 `main.go:120` 的 `initApp()` 里才执行。也就是说构造那一刻
`config.AppConfig` 恒为 `nil`，构造函数里 `if config.AppConfig != nil` 的分支永远走不到。

后果有三个配置项被静默忽略：

| 配置项 | 期望 | 实际（修复前） |
|---|---|---|
| `ASYNC_RESPONSE_TIMEOUT` | 决定短超时客户端 | 恒为硬编码 4s |
| `PLUGIN_TIMEOUT` | 决定长超时客户端 | 恒为硬编码 30s |
| `ASYNC_CACHE_TTL_HOURS` | 决定内存缓存有效期 | 恒为硬编码 1h |

注意 `AsyncSearch` 里的 **select 超时**是在请求时读配置的，所以配小值（如 1s）看起来
"生效"；但配大值（如 12s）时，select 会等 12s，而底层客户端早在 4s 就报错——表现为
"超时配置调大了却没有任何效果"。Dockerfile 恰好把 `ASYNC_RESPONSE_TIMEOUT` 设为 4
（等于硬编码默认值），所以默认部署完全看不出来。

### 改动

超时与缓存有效期改为**调用时解析**，不再在构造阶段读取：

- 新增 `pluginClientTimeouts()` 与 `(*BaseAsyncPlugin).getCacheTTL()`
- `client` / `backgroundClient` 改为懒创建（各自一个 `sync.Once`），首次取用时按
  当时的配置构造；`GetClient()` 的对外签名不变
- `p.cacheTTL` 的 9 处读取改为 `p.getCacheTTL()`
- 首次解析时打一行 `[PLUGIN] 插件客户端超时按当前配置解析：响应 X，处理 Y`，
  让"配置到底生不生效"可以被直接看到，而不是靠猜

### 验证

- `plugin/plugin_config_lazy_test.go`：先构造、后配置 → 取到配置值；无配置 → 退回
  硬编码默认值；重复取用返回同一实例（不丢连接复用）
- 运行时：`ASYNC_RESPONSE_TIMEOUT=11 PLUGIN_TIMEOUT=45` 启动，日志输出
  `响应 11s，处理 45s`，搜索 30 条无回归

## 十三、插件源全量审计（75 个）与失败原因可观测性

### 方法与判别原则

新增门控审计 `main_plugin_audit_test.go`（默认跳过，`AUDIT_PLUGIN_SOURCES=1` 才跑）：
逐个调用已注册插件并按 `refresh` 取一轮，等 35 秒让后台补齐完成后再复核一轮，
两轮都没结果才算"空"。

判别原则（这条比结论本身重要）：

- **只有"解析/结构类"错误**才能断定插件自身失效——这类证据与本机网络无关。
- **403 / 444 / EOF / connection reset 一律不可判定**：它们高度可能是代理出口 IP
  被拒，本机环境不足以区分"站点封了我的出口"与"插件坏了"。
- 任何结论都不从本机网络推广到部署环境（`u3c3`、`gying` 两次教训）。

### 结果

75 个插件：健康 29、抓取失败 20、两轮后仍空 26。

**可判定为站点/插件层面问题（环境无关）**

| 插件 | 现象 | 判断 |
|---|---|---|
| `cldi` | `重试 3 次后仍然失败: %!w(<nil>)` | **代码缺陷**，已修，见下 |
| `clxiong` | 期望 302 重定向，实得 400 | 站点协议变更 |
| `xb6v` | 未找到搜索结果页重定向信息 | 页面结构变更 |
| `erxiao` | `lookup www.2xiaopan.top: no such host` | 域名已不存在 |
| `sousou` | `page 3, type BDY: 567` | 第 3 页失败，前两页可用 |
| `buerchen` | `CHALLENGE_REQUIRED code=42901` | 站点加挑战（先前已记录） |

**不可判定（需在真实部署环境复核，不能据此裁剪）**

- 403：`dyyj` `dyyjpro` `libvio` `miosou` `quarktv` `zlxapp`
- 444：`dy4k` `yunsou`
- EOF：`hunhepan` `leso` `rrbt` `u3c3` `xdpan`
- connection reset：`thepiratebay`

**两轮后仍空的 26 个**里，有一组耗时精确落在 **4.000s / 4.004s / 4.027s**：
`duanjuw` `duoduo` `feikuai` `kpkuang` `pan365` `quark4k` `quarksoo` `sopanya`
`zhizhen`。这正好是 `ASYNC_RESPONSE_TIMEOUT` 的默认值，说明它们是**卡在响应超时
返回了部分空结果**，而不是"真没有匹配内容"。这一组值得单独跟进，但性质是"慢"，
不是"死"。

### 已修：失败原因被丢弃（41 个文件）

审计里 `cldi` 报出 `%!w(<nil>)`，顺着查到一段被复制到 41 个插件的重试循环：

```go
resp, err := client.Do(reqClone)
if err == nil && resp.StatusCode == 200 {
    return resp, nil
}
if resp != nil {
    resp.Body.Close()
}
lastErr = err        // err == nil 时把 lastErr 清空
```

服务器返回非 200 时 `client.Do` 的 `err` 为 `nil`，于是 `lastErr` 被置空，重试三次后
只能报 `%!w(<nil>)` 或干脆只剩"重试 N 次后仍然失败"，**真实状态码彻底丢失**。
这与前几批"让失败可观测"是同一条主线：没有状态码就无法区分反爬、改版与网络抖动。

改动：`err == nil && resp != nil` 时补一个 `err = fmt.Errorf("HTTP 状态码 %d", status)`，
只在原处加信息，不改重试与退避逻辑。41 个文件统一处理，另 5 个经人工核对**不是同一
问题**（`kpkuang`/`hjzhencai`/`miosou` 的赋值在 `err != nil` 分支内；`clmao`/`wuji`
是"不看状态码就返回"，属行为差异，不在此次范围）。

验证：修复后 `cldi` 的报错变为
`[cldi] 搜索第一页失败: ... 重试 3 次后仍然失败: HTTP 状态码 4xx`。

### 测量后记录、未改动

- **19 处插件手写 `Transport: &http.Transport{...}`，没有一处设置 `Proxy`**：
  这些插件完全无视代理配置（包括刚统一的 `PROXY`）。改动需要逐个保留其
  TLS/超时特性，且审计显示这些插件的真实问题在别处，故记录不批量改。
  将来要动，正确做法是 `http.DefaultTransport.(*http.Transport).Clone()`
  再覆盖各自的自定义字段（继承代理与连接池）。
- **`qqpd` 在二维码登录路径内联了 4 个 `&http.Transport{}`**：既丢连接池
  （零值 Transport 退回默认每主机 2 条）也没有代理，且带 `InsecureSkipVerify`。
  属登录链路，非搜索热路径。
- **"52 处自定义 Transport"的旧说法要修正**：真正"每次调用新建独立连接池"的
  只有 `qqpd` 的 4 处（`panyq` 经核对是复用 `client.Transport`，误报）；
  其余 48 处只在构造时建一次，属正常。

## 十四、慢插件是"慢"不是"死"（实证），以及"成功但零产出"的盲区

### 先做实验，再决定要不要改

第十三节里那一组耗时精确落在 4.000s 的插件（`duanjuw` `duoduo` `feikuai`
`kpkuang` `pan365` `quark4k` `quarksoo` `sopanya` `zhizhen`），先用同一批插件、
同一个关键词对比不同预算：

| `ASYNC_RESPONSE_TIMEOUT` | 响应耗时 | 返回条数 |
|---|---|---|
| 4（默认） | 4.01s | **0** |
| 15 | 13.7s | **55** |

**结论：它们是慢，不是死。** 给足预算就有 55 条，默认窗口下一条都拿不到。

紧接着验证后台补齐是否真的把这些结果送达：4 秒窗口下第一次搜索返回 0 条，
等 25 秒后再搜（不刷新）——**0.005s 命中缓存，55 条**。

也就是说设计意图是成立的：快路径按 4 秒返回，慢插件的内容随后由后台补齐进入缓存。
**这 9 个插件不需要改动。**

### 但暴露了一个真盲区：`complete()` 不看出没出结果

同一批日志里写着"慢项 `quark4k` 耗时 4000ms **成功**"，汇总写着"成功 7/9"，
而用户这一轮实际拿到 0 条。两类完全不同的情况被同一个"成功"混在一起。

更严重的是缓存判定。原 `complete()` 只要求"没有超时也没有失败"：

```go
func (o *batchSearchOutcome) complete() bool { return len(o.missing) == 0 && o.failed == 0 }
```

于是"全部成功但零产出"会被判为**完整结果**，按完整 TTL（默认 60 分钟）缓存一整个
周期；而 `shouldBackfill` 又因 `timedOut() == 0` 不触发补齐。空结果就这样被锁住一小时。

这与第一批消掉的债（"插件路径是 TG 缓存污染的同源第二入口"）是同一类问题，
只是触发条件从"失败"换成了"成功但没内容"。

### 改动

- 新增 `observeYield(id, contributed)`：记录每个任务本轮真正贡献的可用结果条数
- 新增 `requireYieldTracking()`：**只由插件路径开启**。插件路径下 4 秒窗口返回空是
  常态；频道路径不开启——频道确实可能没有匹配内容，那种空结果应当照常缓存。
  若把频道路径也纳入，会让"无匹配"的正常批次每轮都重新抓取一遍。
- `cacheTTL`：插件路径下整批零产出直接不写缓存
- `logSummary`：新增"本轮零产出 N"计数与明细名单，并让它单独也能触发输出
  （原来只有失败或超时才输出，全空批次反而一声不响）

### 验证

- `service/batch_search_test.go` 新增 4 个子用例：插件路径整批零产出不写缓存、
  有任意产出即恢复正常判定、频道路径零产出仍照常缓存、零产出不改变失败/超时判定
- 实测冷启动（全新缓存目录）：第一次搜索 4.01s / 0 条，日志输出

```
[searchPlugins] 仙逆：成功 8/9，失败 1，超时未完成 0，本轮零产出 8；失败原因 网络错误×1（示例: ...）
[searchPlugins] 仙逆：本轮零产出（内容需靠后台补齐）: pan365 quark4k feikuai duoduo duanjuw zhizhen kpkuang quarksoo
```

修复前这一行只有"成功 8/9"，完全看不出用户其实一条都没拿到。

## 十五、逐插件搜索结果日志：框架此前在正常路径一行都不打

### 现象与根因

"几十个插件同时搜索时只有少数插件有日志"不是错觉，也不是日志被吞。核实后是三个叠加原因：

1. **框架只在异常路径打日志**。`plugin/plugin.go` 的全部输出点都挂在异常分支上：
   响应超时返回部分缓存、抓取失败回退缓存、缓存更新失败、后台刷新完成。
   一条**正常成功**的插件搜索，框架一行都不输出。
2. **插件自身大多不打日志**。75 个插件里只有 19 个文件的搜索路径含 `fmt.Printf`；
   定义 `DebugLog` 开关的只有 9 个，且**全部为 `false`**。
3. 因此能被看到的，只是少数自己无条件打日志的插件。

### 改动

- `logYields`：**始终输出**一行逐项产出，覆盖每一个真正返回过的任务（含失败的），
  形如 `插件产出 6 个 -> yingso=30 sopanya=0 pan365=0 duoduo=0 quark4k=0 kpkuang=0`。
  它回答的是"某个插件到底跑没跑、跑出几条"，与完整度无关，因此不受
  "仅在有失败时才输出"的限制。
- 失败项也进逐项记录（`=失败`），否则这一行会漏掉失败的插件，看日志的人无从确认它跑没跑。
- 新增可选开关 `PLUGIN_SEARCH_DETAIL_LOG`（**默认关闭**）：打开后每个插件打一行，
  带耗时与失败分类，供逐项排查。默认关是因为几十个插件每次搜索各打一行会把日志冲淡。
- 只作用于插件路径：频道路径 110 个频道逐项列出没有价值，故不启用。

### 验证

- 实测 6 个插件：`插件产出 6 个 -> yingso=30 sopanya=0 pan365=0 duoduo=0 quark4k=0 kpkuang=0`
- 实测含失败的组合：`插件产出 4 个 -> buerchen=失败 yingso=30 erxiao=失败 libvio=失败`

## 十六、手写 Transport 一律缺 Proxy（49 处，已补 + 守卫）

### 结论修正

第十三节说"19 处手写 Transport"，那是 `Transport: &http.Transport{` 这一种写法的计数。
按块扫描全部 `&http.Transport{`（含赋给变量的），实际是 **49 处**，分布在 46 个文件。

而且它们**并不业余**：绝大多数显式设了 `MaxIdleConns` / `MaxIdleConnsPerHost` /
`MaxConnsPerHost` / `IdleConnTimeout`。唯一缺的是 `Proxy` 字段——零值含义是
"永远直连"，于是**部署方配了代理，这些插件全部静默失败**，而 `DefaultTransport`
已被 `TuneDefaultTransport` 接好代理，两条路径行为不一致。

### 改动

- 新增 `util.ProxyFuncForTransport()`，按项目统一规则解析（`PROXY` → `HTTPS_PROXY` →
  `HTTP_PROXY` → `ALL_PROXY`，并按 `NO_PROXY` 放行直连），供插件手写 Transport 时赋值。
- 49 处统一补上 `Proxy: util.ProxyFuncForTransport(),`，其中 45 个文件补了 `pansou/util` 导入。
- 新增**防回归守卫测试** `plugin/plugin_transport_proxy_test.go`：直接扫描源码，
  任何手写 Transport 缺少 `Proxy` 就失败。已做对照验证——删掉 `zxzj` 的一处后
  测试精确报出 `zxzj/zxzj.go:38`。

### 验证

- 全部 49 处扫描通过；`util/http_util_test.go` 新增用例确认该助手按配置解析代理并遵守 `NO_PROXY`

## 十七、两处自我纠正（都被本人实验推翻）

### `erxiao`：域名**并未**消失

第十三节把 `lookup www.2xiaopan.top: no such host` 判为"域名已不存在"。用公共 DNS
交叉验证后推翻：`nslookup www.2xiaopan.top 8.8.8.8` 正常返回
`xiaomi666.cf-site.1o.ee` → `104.18.42.163`（Cloudflare）。

即**本机解析失败是环境问题，不是域名消失**。该插件退回"不可判定"。这是第三次
同类教训（前两次是 `u3c3` 与 `gying`）：本机网络不足以判断源站死活。

### `clxiong`："重试复用请求体"假设被对照实验推翻

审计里 `clxiong` 报"期望302重定向，但得到状态码: 400"。我一度认定根因是重试循环
复用同一个 `req`、body 已被消费。**做了对照实验后推翻**：把代码改回 `client.Do(req)`
（即所谓"有 bug"的写法），测试服务器三次收到的请求体**都是完整的**。

原因是现代 Go 的 `Transport.roundTrip` 会用 `GetBody` 把请求体回卷
（`strings.NewReader` / `bytes.Reader` 这类由 `NewRequest` 自动填好 `GetBody`），
所以复用请求在重试里是安全的。改动已全部撤销（`git checkout` 还原 + 删除测试），
不留"修了个不存在的问题"的代码。把这个反例记下来，避免以后再"修"一次。

### `clxiong` / `xb6v` 的实际情况

站点探测（含代理）：

| 站点 | 直连 | 经代理 | 插件现象 | 判断 |
|---|---|---|---|---|
| `www.cilixiong.org`（clxiong） | 200 | 200 | 期望 302，实得 400 | 站点搜索**行为变更**：直接返回一个"信息提示"页（3 秒后 `history.go(-1)`），不再是重定向 |
| `www.66ss.org`（xb6v） | 000 | **200** | 未找到搜索结果页重定向信息 | 站点**可达**，插件预期与现状不符 |
| `www.2xiaopan.top`（erxiao） | 000 | 000 | DNS 解析失败 | **不可判定**（公共 DNS 正常） |

两个站点都没有失效，是插件实现落后于站点现状；按新流程适配需要先摸清站点当前
的搜索交互，属独立任务，不在本次范围。

## 十九、统一 JSON 实现：清理 14 处绕过封装 + 守卫

项目约定业务代码只用 `pansou/util/json`（sonic 封装），但仓内有 **13 个业务文件**仍在直接
`import "encoding/json"`（另 3 个文件是混用：同一个文件里既用封装又用 stdlib）。

先给封装补齐调用方真正需要、但原先没暴露的能力，否则"只用封装"这条约定无法在全部调用点成立：

| 补齐项 | 说明 |
|---|---|
| `RawMessage`、`Number` | 别名 stdlib 同名类型，sonic 原生支持 |
| `NewDecoder`、`NewEncoder`、`Decoder`、`Encoder` | 注意 **sonic v1.14 的 `NewDecoder` 返回值而不是指针**，与 stdlib 不同，靠编译探针确认 |

迁移覆盖 14 个文件（`Marshal`/`Unmarshal`/`NewDecoder`/`NewEncoder`/`RawMessage`/`Number`
共 33 处调用）。三处混用文件采用"删掉 stdlib 导入、把调用改到已有封装别名上"的方式，避免重复导入。

现在全仓只剩 `util/json/adapter.go` 一处 `encoding/json`，而它的职责正是别名 stdlib 类型、
让调用方不必自己引。新增守卫用例 `TestNoDirectEncodingJSONOutsideWrapper` 扫描全仓强制这条约定
（对照实验：往 `plugin/sdso/sdso.go` 注入一行导入，守卫立即失败并点名该文件）。

`util/json` 覆盖率同时从 **0.0%** 提到有实际断言（编码解码往返、RawMessage 解到字段、
`UseNumber` 下大整数不丢精度）。

### 一次"纠正的纠正"——记录在此以免后人重犯

`panlian` 的重复 json tag 我最初判断"两个字段都被静默丢弃"。启用 JSON 统一后我怀疑该结论
依赖 `encoding/json` 语义、而生产走 sonic，于是跑了个探针看到 `TypeName="科幻片"`，据此写下
"sonic 不会丢弃，我的原判断错了"。

**这次纠正本身是错的**：那个探针跑在**已经修好 tag 的结构**上，根本没构成冲突，所以它什么
也没证明。重新用真正冲突的结构实测：

```
修复前结构（Type 与 TypeName 同为 json:"type_name"）+ sonic:  Type="" TypeName=""   ← 两个都丢
修复后结构（Type 为 json:"type"）+ sonic 给两个 key:           Type="电影" TypeName="科幻片"
```

结论：**sonic 与 encoding/json 在这一点上行为一致**，最初判断成立，改动确实修复了真实数据丢失。

教训（第 5 次同类）：探针必须真的触发被断言的条件。前面 4 次（`u3c3`、`erxiao` 域名、
`gying` 站点、自造的 3 秒批次预算）都是"从小样本/单点推广"，这次是"用不触发条件的探针推翻
正确结论"，方向相反但根因相同。

顺带把该用例的冲突结构改用 `reflect.StructOf` 在运行时构造：源码里写两个同 tag 字段会触发
`go vet` 的 struct field repeats json tag，运行时构造同样走到 sonic 的字段解析逻辑，
且保持 vet 零告警。

### H3 也已修：磁盘→内存回填改按剩余寿命

又不校验新鲜度（`search_service.go` 注释明写"不检查新鲜度"），短 TTL 分流被整个绕过。

`GetLastModified` 同路径，无额外 I/O），回填时按 `time.Until(expiry)` 计时；若剩余已为负
则直接判为未命中，不复活过期条目。

## 二十一、共享插件实例上逐请求写字段（并发 H1 已修）

插件实例来自全局注册表，跨请求共享。service 层此前每个请求都往同一实例上写：


而读点有两类：插件调用点普遍传 `p.MainCacheKey` 给 `AsyncSearchWithResult`（**106 处**），
框架内部还有 3 处读 `p.currentKeyword`。两个并发请求（或请求与后台补齐）互相覆盖，
A 关键词的结果会被写进 B 关键词的缓存槽。

讽刺的是 `plugin/plugin.go` 顶部的注释早已为 `ExtContextKey` 修过同一隐患——

- 新增 `plugin.ExtMainCacheKey`，service 把它注入每份 per-request 的 ext 副本

- 关键词不再从实例读：`updateMainCacheWithFinal` 补上 `keyword` 参数（它原先没有，所以只能读
  `p.currentKeyword`），3 处读点全部改用参数透传；`SetCurrentKeyword` 标注 Deprecated。

  且其值本身由 keyword+plugins+ext 推出，算进摘要纯属冗余。

service 侧对共享字段的写入已清零（grep 确认 0 处）。

**对照实验（决定性）**：把 `resolveMainCacheKey` 退回"只用传入值"，并发用例里**每个**关键词

## 二十四、DelayedBatchWriteManager 统计字段跨锁域竞争（并发 H2 已修）

`WriteManagerStats` 里两类字段的写法不一致：计数器用 `atomic.AddInt64`（对的），

却是裸读写——它们是 `time.Time`/`string`/`int`，无法直接用 atomic，于是被漏下了。

**顺手挖出更隐蔽的一处**：`GetStats` 与 `GetWriteManagerStats` 都是 `stats := *m.stats`
整结构复制。复制不是原子的，会与 `atomic.AddInt64` 的写入竞争——比裸字段更难看出来。
改为 `snapshotStats()` 逐字段 `atomic.Load*` 读计数器、元信息走锁。

验证（对照实验决定性）：`TestFlushMetaConcurrentAccess` 在 `-race` 下跑 2 写 2 读；

## 二十五、主缓存读-改-写非原子（缓存 M3 已修）

`injectMainCacheToAsyncPlugins` 注入的 `cacheUpdater` 干的是：

```
Get(key) → 反序列化 → mergeSearchResults(现有, 新增) → 序列化 → Set(key)
```

同关键词下多个插件并发完成时（异步插件的常态），两个调用读到同一份旧值、各自只把自己
那部分并进去再写回，**后写的覆盖先写的**——先完成那个插件的结果凭空消失，表现为
"明明搜到了，结果里却只剩一个源"。

修法：整段临界区纳入按键分条的锁（`service/main_cache_lock.go`，64 条，按缓存键内容做
FNV 哈希）。用分条而不是单把大锁：只有同一个缓存键的更新需要互斥，不同键之间不该排队，
否则一个慢键会拖住所有关键词的缓存更新。

**端到端测试的困难（如实记录）**：直接断言"并发合并不丢结果"需要驱动插件完成路径
（`AsyncSearch` 的同步/后台完成分支 + 工作池）。尝试过程中两次踩到真实机制：

- 用**同一个插件实例**并发 8 次不行——插件级缓存键含插件名，会被去重成只搜 1 次；
  真实场景必须是 8 个不同名插件写同一个主缓存键。
- 改成 8 个不同名实例并走注入路径后，探针显示 `cacheUpdater` 始终未被调用，排查耗时已
  超过收益，遂停手。因此本次测试覆盖的是**锁的语义**（同一键串行、不同键不互斥、
  解锁后放行、等值字符串落到同一条），而非端到端合并。

对照实验：把 `lockMainCacheKey` 换成空操作，`TestLockMainCacheKeySerializesSameKey` 立刻
以"同一个缓存键上有两个持有者同时进入临界区"失败。

**复核方式（部署环境）**：多插件并发搜索同一热词，观察 `merged_by_type` 各源条数是否与
逐插件单独搜索的条数之和一致；修复前会随机少源。

## 二十六、磁盘缓存写入原子化（缓存 H6/H7 已修）

`DiskCache.Set` 直接 `ioutil.WriteFile` 到最终路径。进程在写一半时被 kill（容器滚动更新、
OOM、宿主机重启）会留下**截断的文件而元数据仍然有效**，`Get` 于是把半截 JSON 交给反序列化
——故障表现是"结果是空的/残缺的"而不是缓存未命中，排查时极易误判成上游插件故障。
`saveMetadata` 同样非原子，半截元数据会让缓存项"存在但读不出"。

修法 `writeFileAtomic`：写临时文件 → `fsync` → `rename`。rename 在同一文件系统内原子，
读者要么看到旧内容、要么看到完整新内容；`fsync` 防止"rename 已生效但数据还在页缓存"时
断电留下空文件。`Set` 与 `saveMetadata` 都改用它。

**顺手删掉一处多余操作**：原代码在写新数据前先 `os.Remove` 旧文件。但 `getFilename` 是键的
MD5，新旧文件**同路径**，rename 本就会整体覆盖——预先删除非但无用，反而把"写一半崩溃"的
窗口重新打开，且删不掉时错误被丢弃。

**错误不再静默**：`Set` 里元数据保存失败后的清理、`Delete` 里两个文件的删除，原先
`os.Remove` 返回值全部丢弃。现在 `IsNotExist` 视为正常（过期清理、重复删除都会走到），
其它错误返回或打印——否则会变成"元数据已删但文件永远留在磁盘上"的静默泄漏。
`Delete` 无论文件是否删干净都要更新内存元数据表，否则内存会一直引用不存在的项。

**测试的边界（如实说明）**："崩溃窗口期不可见半截数据"这一点是**由构造保证**（rename 原子性），
不是测出来的——单测无法在任意时刻 kill 自己。用例锁住的是这个构造所依赖的不变量：
整体替换、失败时保留原内容且不留临时文件、目录不存在时报错而非静默成功、Set/Delete 后
无 `.tmp` 残留、并发读写时命中值只可能是两个完整载荷之一（200 KiB 载荷交替写 + 3 读，
回归网）。

对照实验：把 `writeFileAtomic` 换成直接 `os.WriteFile`，失败路径的两个用例
（保留原内容+指明失败环节、目录不存在时报错）立刻失败。

**已知残留（次要）**：被 kill 留下的 `.tmp` 文件不会被 `loadMetadata` 计入 `currSize`
（它按 `<name>.meta` 查找，找不到就跳过），也不会被 LRU 清理，属可见但无害的空间泄漏；
下轮可加启动清理。

## 二十七、循环内 defer 关闭响应体（资源 中项已修，且**修正了审计数字**）

审计记的是"5 处循环内 `defer resp.Body.Close()`"。用花括号深度写了精确检测器后，**词法上**
落在循环体内的候选是 **10 处**，但逐处定性后：

| 定性 | 数量 | 位置特征 |
|---|---|---|
| **真缺陷（已修 4 处）** | 4 | `for i := 0; i <= p.retries; i++` 重试循环体内直接 `defer` + `continue`。重试 N 次就同时压着 N 个未关闭的响应体，连接也不归还连接池。quarksoo / quark4k / bixin / pan666 |
| 误报：分支内立即 return | 4 | `if err == nil && resp.StatusCode == http.StatusOK { defer resp.Body.Close(); ...; return }`——defer 当场触发。gaoqing888 / dyyjpro / quarktv / lingjisp |
| 误报：每轮即时调用闭包 | 2 | 循环体是 `func(page int){...}(page)`，defer 作用域就是那一轮。sousou / hunhepan |

所以审计的"5 处"两头都不准：候选数不对，而且 6/10 是正确代码。**"循环里出现 defer"不等于缺陷**
——判据是 defer 的作用域是否被限制在单轮内（分支内 return 或每轮闭包）。

4 处改法是读完立即 `resp.Body.Close()`，并把该分支的注释写明原因，避免后人照着别处改回 defer。

**防回归守卫**：`main_body_close_guard_test.go` 的 `TestNoDeferBodyCloseInsideRetryLoop`
只认"循环体内且该循环体内存在 `continue`"这一种形状——刻意窄，因为另外两种相似写法是正确的，
不能误伤。对照实验：把 pan666 的修复还原回 `defer`，守卫立刻 FAIL 并点名
`plugin/pan666/pan666.go:213`。

**本条仍未做**：72 处 `io.ReadAll` 无上限。这一项不能批量盲改——各站点响应体量级差异大，
统一封顶可能截断合法的大响应，需要先把"从上游取的数据"与"本地/小接口数据"分开再逐个定上限。

## 二十八、上游响应体读取封顶（资源 中项已修，77 处）

全仓 `io.ReadAll(resp.Body)` **恰好 72 处**（审计数字正确），另有 4 处别名的响应体
（`jsResp`/`challengeResp`/`infoResp`/`qrResp`）与 1 处在 `util/http_util.go` 内，合计 77 处。
上游是第三方网盘站点，返回体量完全由对方决定，而**插件是并发跑的**——几十个插件同时撞上
一个异常大的响应就足以把进程内存打满。这不是假想：返回体既可能被投毒，也可能只是页面
异常膨胀。

新增 `util.ReadAllLimited(r, limit)` 与 `MaxUpstreamResponseBytes = 16 MiB`。取 16 MiB 是因为
正常插件响应在一两 MiB 量级，留了一个数量级余量；真出现超过它的合法响应，宁可让该插件按
"读取失败"报错也不要静默撑爆内存——**失败是可见的，OOM 不是**。

实现要点：用 `io.LimitReader` 读 **limit+1** 字节。多读的那 1 字节是用来区分"正好等于上限"
与"超过上限"的——只读 limit 字节时无法判断流是结束了还是被截断了。用例同时验证了边界
（正好等于上限成功、多 1 字节失败）与"超限即停"（用一个读不完的流，读完就会耗尽内存）。

**迁移过程本身暴露了两个问题**，都不是我事先想到的：

1. 我的迁移脚本按 `package util` 跳过文件，于是 `util/http_util.go:298` 那处**漏了**——
   而它恰恰是所有插件共用的基础工具函数。是守卫测试第一次运行时报出来的。
2. 守卫第一版被**我自己的注释**误伤：`http_body.go` 里那句"全仓原先有 70+ 处裸
   `io.ReadAll(resp.Body)`"被当成违规代码。已改为先剥行尾注释再匹配。

迁移 49 个文件、77 个站点，同时处理了 28 处新增 `pansou/util` 导入与 42 处因 `io` 不再使用

### SHARD_COUNT：把文档承诺兑现

README 一直把 `SHARD_COUNT` 列在环境变量表里，而代码从来没读过它——分片数由
`runtime.NumCPU() * 2` 算。文档承诺了一个不存在的开关。选择**实现**而不是删文档：用户的
预期是"设置它有用"，删文档是改了约定而不是兑现约定。

`resolveShardCount`：显式值优先，非 2 的幂向上取整（分片按掩码取模，必须是 2 的幂），
一律夹到 [4, 64]；非法值忽略并打印回落原因——免得一个手滑的 `SHARD_COUNT=0` 变成零分片缓存。

验证：`config` 2 个用例（默认 false、nil 安全、只认 true/1）、`util/cache` 3 个用例
（生效、非 2 的幂取整、0/负数/非数字/空白回落、超大夹到 64、超小抬到 4、未设置按 CPU 推算、
多核封顶）。README 环境变量表同时补上两个开关的准确语义。

## 三十一、重试实现收敛：公共组件 + 首个试点（33 处中已迁 1 处）

全仓 30 多处复制粘贴的重试循环形态高度一致：`for i := 0; i <= p.retries; i++`、固定
`time.Sleep(500 * time.Millisecond)`、每处都要自己处理"最后一次不再等待""错误怎么包装"
"响应体在循环里怎么关"——其中 4 份就是在这里把 `defer` 写进循环体（见 §二十七）。

新增 `util.DoWithRetry(cfg, fn)`：
- `RetryConfig` 支持固定间隔（`BaseDelay == MaxDelay`，即既有形态）与指数退避 + `MaxDelay` 封顶。
- `Jitter` 加 ±25% 抖动。**抖动不是装饰**：全仓写死 500ms，上游一旦限流，所有并发插件会在
  同一时刻重新打过去，把限流变成雪崩。
- `OnRetry` 回调供观测；返回的错误保留原始错误链（`errors.Is` 仍可判定），只在最外层加上
  尝试次数。
- 成功路径不等待（有用例锁住，否则每次正常请求都会被拖慢）。

首个试点 quarksoo 迁移后**行为逐项对齐**并实测：3 次尝试（`retries=2` +首次）、
总耗时 1.01s（固定 500ms ×2）、耗尽后返回 `重试 3 次后仍失败: API返回非200状态码: 500`
（保留上游原因）、返回条数 0。用例覆盖"先 500 两次再 200 应成功"与"一直 500 应报错且
尝试次数正确"。`BaseURL` 由 const 改为 var 以便测试指向本地假服务器。

### 更正：那个"0 请求 / nil 错误 / 0.00s"的真实原因（我连续误判了两次）

第一次判成"缓存未按关键词隔离"，第二次判成"框架缓存命中属既有设计"。**两次都错。**

真正的原因是 **`config.AppConfig.AsyncResponseTimeoutDur == 0`**：这种配置下框架会**立刻返回
空结果且不报错**，搜索转到后台继续跑。于是用例看到的是"零请求、nil 错误、0.00s"——三个特征
全都指向"什么都没发生"，而实际上请求在后台发着。这个签名极易被误判，我已把它写进用例注释。

定位方式来自 YG 的提示："可以直接清理数据缓存 cache 目录来测试，这样不换关键词也可以"。
照做后发现**只要把缓存目录指向用例专属的临时目录、并把 `AsyncResponseTimeoutDur` 给足，
同一关键词、不带 `refresh` 也能稳定跑通**（`-count=2`：4.04s = 2 轮 × 2 用例 × 1s，请求都发生）。
这也顺带说明：失败结果不会被缓存（否则同关键词的第二个用例仍会命中），所以此处根本不涉及
关键词隔离问题。

最终用例简化为"同一关键词 + 独立缓存目录"，去掉了为绕开"缓存"而加的关键词区分与
`refresh`——那两样都是基于错误诊断加的。教训与 §二十五 那次同类：**先把现象判成缺陷之前，
先确认触发条件真的成立**（这次连"是缓存"这个前提都没验证）。

**最初的下错结论记录如下（保留以备对照）**：第二版用例出现"0 次请求、nil 错误、0.00s"，我一度
判断是"缓存未按关键词隔离"的缺陷。实际查明是**框架的既有设计**——同一关键词的结果（含
空结果）会被缓存，命中即不发请求，这是缓存正常工作。两个用例都必须显式带 `refresh: true`
并且用不同关键词，否则测的是缓存而不是重试。结论：**在把现象判成缺陷前，先排除"这是
设计如此"**。

剩余 3 处同形循环（`grep 'for i := 0; i <= p.retries'`）与其它形态的重试共 30 余处待迁移，
属机械替换，但每处的错误文案与循环后用法不同，需逐个人工确认——不做批量替换。

## 三十三、重试迁移第二批：返回响应的同源家族（mizixing + yiove）

`for i := 0; i <= p.retries` 那批是"读体后返回结果"；这批是**另一个复制粘贴家族**：
`for attempt := 0; attempt < maxRetries; attempt++`、返回 `*http.Response`（由调用方读体）、
已有指数退避 `retryBaseDelay * 2^attempt`、保留 `lastErr`。mizixing 与 yiove 的循环体**逐字相同**
（连我之前修的 `%!w(<nil>)` 注释都在，证实同源）。

迁移时保留语义：`Multiplier: 2` 对应 `2^attempt`；`DoWithRetry` 天然跳过最后一次等待，
等价于原先的 `if attempt < maxRetries-1`。失败时状态码仍被带出，`%!w(<nil>)` 那个回归锁进了用例。

**用例耗时本身就是退避语义的证据**：3 次尝试 0.60s = 200ms + 400ms（`retryBaseDelay × 2^attempt`），
2 次尝试 0.20s = 单次 200ms。

这个过程里我又犯了一次编辑错误：把原循环后的 `return nil, fmt.Errorf(...)` 用正则删掉时留下一个多余
的 `}`，且第一次修正因为没料到中间有个空行而匹配失败（`}\n\n}` 而非 `}\n}`）。两次都是先看到 `go build`
报 `expected declaration, found '}'` 才定位——**编辑脚本的断言必须打在真正的位置上，否则删多删少都
只会在编译期暴露**。

同家族的 kkmao、ypfxw（用 `backoff` 变量）、yulinshufa（收尾文案不同）、javdb（限流专用）、
gaoqing888/dyyjpro/quarktv（循环内 return + cancel 的另一种形状）仍需逐处迁移，形状不同不批量做。

## 三十四、重试迁移第三批：kkmao / ypfxw / yulinshufa

kkmao、ypfxw 与 §三十三 的 mizixing/yiove **同形**（只差延迟来源：一个是入参 `baseDelay`，
一个是常量 `retryBaseDelay`），循环体连注释都一致，故按同一模板迁移；区别只在 `RetryConfig.BaseDelay`
的取值。

yulinshufa 是**变体**，需单独对齐两处语义：
- 它把等待放在**尝试之前**（`if attempt > 0` 先睡再发），组件是失败后等。二者等价：原第 k 次尝试前等
  `2^(k-1)×200ms`，组件在第 j 次失败后等 `2^j×200ms` 再发第 j+1 次，逐项相同。所以
  `Multiplier: 2` + `BaseDelay: 200ms` 精确还原原退避曲线。
- 它的 debug 日志打在"即将重试"处、**次数从 1 起计**；组件回调的 `attempt` 是 0 起的失败序号，
  所以日志里要写 `attempt+2` 才是原来的"第几次请求"。这类差一错误若不对齐，日志就会从"第 2 次"
  开始，排查时误导人。

kkmao 补了行为用例，**耗时即证据**：3 次尝试 0.31s ≈ 100ms + 200ms，退避曲线仍生效；上游一直 403 时
错误里必须带 `403` 且不得出现 `%!w(<nil>)`。

至此同源家族（返回 `*http.Response`、带指数退避）已迁移 5 处。全仓 `for attempt := 0` / `for retry := 0`
形态仍有 26 处，形状各异（限流专用、循环内 return + cancel、先睡后试、固定间隔等），继续逐处核对迁移。

## 三十五、重试迁移第四批：gaoqing888（循环内建 context 的形状）

`fetchBody` 是另一种形状：**每次尝试各自 `context.WithTimeout`**，即超时按尝试计算、而不是整轮
共享一个。迁移时这个语义必须保留——ctx/cancel 建在闭包内（`defer cancel()` 在闭包返回时释放，
不会跨轮累积），而不是提到循环外。

其余语义同样逐项对齐：退避 `200ms × 2^attempt` → `Multiplier: 2`；成功即读体返回；
失败带 `HTTP %d` 状态码。原实现对"建请求失败"是立即返回不重试，迁移后会被重试——这个差异无害
（同样的输入必然同样失败），但记录在案。

补了 3 个用例，其中最关键的是**每次尝试的超时必须生效**：上游 handler 故意挂 2 秒，单次超时
100ms、3 次尝试，实测 `elapsed` 约 0.9 秒（300ms 超时 + 200ms + 400ms 退避），远小于上游的 2 秒
——证明确实按次超时而不是被拖成整轮。

**注意用例耗时不能直接当证据**：`httptest.Server.Close()` 会等未完成的 handler 结束，所以该用例
报告的 2.80s 里含服务器关闭等待的 2 秒；真正的证据是断言里单独测的 `elapsed`。前几批我用
"测试耗时 = 退避曲线"作证据时，恰好因为 handler 立即返回而没有这个偏差，但判读方式应统一为
**测量目标代码本身的耗时**。

## 三十六、重试迁移第五批（dyyjpro / quarktv / lingjisp）+ 补上手写无界读取守卫

### 守卫的漏洞：别名与手写实现能逃过文本匹配

§二十八 把 77 处上游响应体读取封顶 16 MiB，但守卫是按 `io.ReadAll(` **文本匹配**的。于是：

- `plugin/quarktv/quarktv.go` 里的本地包装 `ioReadAll` 自己 `make` 缓冲、在 `for {}` 里无限

- 新守卫扫描后又抓到 `plugin/lingjisp/lingjisp.go:258` 的同一种手写循环。

## 三十八、重试迁移第七批：jupansou / lou1 / daishudj（改用括号配对的通用替换）

这三处与 §三十七 的模板只是**边缘差异**（jupansou 的退避写作 `200 * time.Millisecond * time.Duration(1<<attempt)`，
顺序与其他文件相反；另两处循环头/收尾的空行不同），精确模板匹配失败。改用**基于括号配对的通用替换**：
定位 `for attempt := 0;` 行 → 配平括号取循环体 → 从体内提取循环次数与退避基准表达式 → 替换
整个 `var lastErr error … return nil, …` 区间。这样不依赖空格与字面量写法，适用于同族的所有变体。

**又一次留下多余的 `}`**（`return nil, …` 那行不含函数收尾括号，而新块自带 `}`），三处都是靠
`go vet` 报 `expected declaration, found '}'` 定位。这已经是第二次同类问题，结论是：
**这类替换不需要额外写守卫——编译器就是守卫**，但替换脚本必须把"函数收尾括号是否被包含进区间"
当成显式约束，否则每次都要靠编译错误回头修。

### 同族≠同行为：4 处**不可**按模板迁移

对剩余 A 族逐个核对退避形状，发现它们根本不是同一种退避：

| 插件 | 实际退避 |
| --- | --- |
| xiaoyu | **线性**：`time.Duration(attempt) * 200ms` |
| yunsou | 错位指数：`2^(attempt-1) * 200ms`（先睡后试） |
| aikanzy | 用变量 `backoffTime` |
| zlxapp | **完全不睡**（无退避） |
| javdb | 限流专用：只在 429 时重试，`resp.StatusCode != 429` 即返回 |

这直接说明**不能按"A 族"批量迁移**：xiaoyu 若套用 `Multiplier: 2` 会把它从线性退避**改成指数退避**，
那是改行为不是收敛实现。zlxapp 压根没有退避语义，迁进带退避的组件同样是改行为。javdb 只在 429
重试的语义组件也不表达。这四处各自需要判断，不进本批。

## 三十九、RetryConfig 补 DelayFunc，据此迁移 yunsou 与 xiaoyu

### 为什么必须加 DelayFunc

§三十八 逐处核对退避形状后发现，"退避曲线"根本不是只有倍率一种：xiaoyu 是**线性**
（`attempt × 200ms`）、javdb 是**区间随机**（限流场景，故意打散重试时刻）、aikanzy 用变量、
zlxapp **完全不退避**。只提供 `BaseDelay × Multiplier` 一种表达，就等于逼着这些站点要么改行为、
要么永远留在组件外——两者都不可接受。

因此 `RetryConfig` 增加 `DelayFunc func(attempt int) time.Duration`，优先级最高（非 nil 时
`BaseDelay`/`Multiplier`/`Jitter` 全部不参与），返回 0 表示该次不等待。用例覆盖：线性三项取值
逐项校验、以及"返回 0 时真的不等待"（并实测重试耗时，避免只是配置写了而实现仍在睡）。

### 迁移

- **yunsou**：与 §三十四 的 yulinshufa 同形（先睡后试、`2^(attempt-1)×200ms`），用
  `Multiplier: 2` + `BaseDelay: 200ms` 精确还原。
- **xiaoyu**：用 `DelayFunc` 表达线性退避。映射关系写进注释：原实现第 k 次尝试前等 `k×200ms`，
  组件在第 j 次失败后等待再发第 j+1 次，故 `DelayFunc(j) = (j+1)×200ms`。次数保持 `maxRetries+1`
  （原循环条件是 `attempt <= maxRetries`，容易在迁移时误写成 `maxRetries`）。

**这一步的意义不是多迁了两个插件，而是把"异构退避"从"无法收敛"变成"可以收敛"**——javdb 的
区间随机、zlxapp 的零退避现在都有了归宿，只剩逐处确认调用语义。

xiaoyu 只有既有测试、无重试专项用例，此点如实记录。

## 四十、重试迁移第八批：aikanzy（附带修掉状态码丢失）、zlxapp

### aikanzy：迁移顺带修掉一个真缺陷

原实现只保存 `client.Do` 的 err，**状态码非 200 时 err 为 nil**，于是重试耗尽后报出的是
`重试 N 次后仍然失败: %!w(<nil>)`——真实状态码丢失、完全无法定位。这正是 §十九 在 41 处修过的
同一个问题，aikanzy 漏网。迁移时把状态码带出，并用例锁住（上游一直 404 时错误必须含 `404` 且
不得出现 `%!w(<nil>)`）。退避为 `backoffBase(200ms) × 2^(k-1)`，用 `Multiplier: 2` 还原；
实测 4 次尝试 1.41s = 200+400+800，与曲线一致。同时保留原"每次重试克隆请求"的意图。

### zlxapp：**更正上一轮的判断错误**

§三十八 我写"zlxapp 完全不睡（无退避）"——**这是错的**。它确实有退避，而且比我以为的更好：
`attempt × 200ms` 线性，用 `time.NewTimer` + `select` 实现，**等待可被请求上下文取消**。
错因是分类脚本只 grep 了 `time.Sleep(`，而它根本不用 Sleep。教训：**用单一文本模式给代码分类
会漏掉等价写法**，这正是前面"守卫只能挡住它认识的写法"同一个病根。

迁移时保住两个特点：线性退避留在闭包内（组件侧 `DelayFunc` 返回 0），以及可取消等待原样保留。
**已知差异如实记录**：上下文取消后组件仍会把剩余尝试次数走完（每轮立即失败），原实现是立刻返回；
差别只在取消瞬间，且不再有等待。

### 一个待补的组件能力

zlxapp 与 javdb 都提示同一件事：`RetryConfig` 的等待是 `time.Sleep`，**不可取消**。若给组件加
`WaitFunc`（默认 Sleep，可注入带 context 的实现），则这批"可取消等待"的站点能更自然地收敛，
也能让取消语义在全仓统一。已记入清单。

## 四十一、重试迁移第九批：javdb（A 族清零）

javdb 的语义与其它插件**都不同**，逐项对齐：
- **只在 429 时重试**：非 429（含 5xx）一律直接返回该响应，由调用方判断（用例锁住：非 429 时
  只请求 1 次、不置限流标志、返回原状态码）；
- 退避是**随机区间** `MinRetryDelay~MaxRetryDelay` 秒，故意打散重试时刻避免加压——用 `DelayFunc`
  表达，倍率退避在这里是错的；
- 次数 `MaxRetryOnRateLimit+1`（原 `attempt <= MaxRetryOnRateLimit`）；
- 重试用尽时置 `rateLimited` 标志、返回带原因的专用错误，而**不是**笼统的"重试 N 次后仍失败"。
  组件返回错误时优先返回这个专用错误，因为它带限流原因、更有用。

关键点：`MaxRetryOnRateLimit` 默认为 **0**，此时 `Attempts=1`，第 0 次即命中"放弃"分支——与原实现
"设为 0 则不重试"一致。这条最容易在迁移时写错成"仍重试 MaxRetryOnRateLimit 次"，用例专门锁住。

**A 族（返回 `*http.Response` 的 12 处）到此清零**：mizixing、yiove、kkmao、ypfxw、mikuclub、
jsnoteclub、duanjuw、alupan、jupansou、lou1、daishudj、javdb。余下 C 族 7 处 + 其它形态，
以及既有的吞错与端到端用例两项。

### 新增 AbortError：把"不该重试"变成可表达

仓里的重试并不都是"任何失败都值得再来一次"：4xx（目标明确拒绝）、登录失效（cookie 过期）、
响应格式不对（再试还是不对）——继续重试只是白等。此前这 4 处无法收敛，只能各自保留循环。

新增 `util.Abort(err)` + `ErrAborted` 哨兵：
- `DoWithRetry` 遇到被标记的错误**立即停止**，不等待、不触发 `OnRetry`（用例实测：调用 1 次、
  重试回调 0 次、耗时 <200ms）；
- **不包装成"重试 N 次后仍失败"**——那会误导，因为它第一次就决定不重试了（用例显式断言）；
- `errors.Is` 既能拿到原始错误、也能判定 `ErrAborted`；
- `Abort(nil)` 必须是 nil（否则会把成功变成中止），单独有用例。

### panlian 迁移（首个 AbortError 消费者）

## 四十三、吞错处置（一）：nsgame 半截数据当成功、磁盘写失败无痕

26 处吞错（23 处 `_ =` + 3 处 `X, _ :=`）逐处定性，本轮先处置文档点名的两处真缺陷。

### nsgame：读体失败返回"半截 data + nil error"

`data, _ := util.ReadAllLimited(resp.Body, ...)` —— 读体失败被丢弃，调用方拿到的是被截断的会话
数据却毫无察觉，还会被当成成功继续走。已改为取错误并返回。

顺带把顺序调正：**先判状态码再读体**。非 200 的响应体本来就要丢弃，先读它既浪费、又可能因为
错误页过大而报出"响应过大"，把真正有用的状态码盖掉——那会让排障信息更差。

### 磁盘缓存写失败：`_ =` 让它完全没有痕迹

`enhanced_two_level_cache.go` 的异步磁盘写是 `_ = c.disk.Set(...)`。后果很隐蔽：**内存里还有值，
一切看起来正常，直到重启后缓存全空，且没有任何线索**。

异步写没法把错误回传给调用方，所以处置是"让它可观测"而不是"返回错误"。但直接每次都打日志有害
——磁盘写满时每次 Set 都失败，会把日志刷爆、反而淹掉别的问题。因此加**限流**：30 秒窗口内只打
一次，并把期间累计的失败次数一并报出（**数量这个信息不能丢**）。用例锁住限流行为：首次打印、
窗口内累计计数、窗口外打印后清零累计。

### 一个测试自身的坑

我原本还写了一个"磁盘写失败时 Set 仍应成功"的用例，结果 panic。查明原因不是 `c.disk` 为 nil
（构造函数必然创建磁盘缓存），而是**构造函数依赖全局 `config.AppConfig`**，测试进程里为 nil。
也就是说：这个方向要测得先注入配置。无效用例已删除并如实记录原因——**测试失败时要先确认是
被测代码的问题还是测试环境的问题**，否则很容易把环境问题写成"发现缺陷"（本轮之前的 zlxapp
误判就是同类错误的另一种形态）。

## 四十四、吞错处置（二）：check_service 的两组，一真一假

### checkAliyun 的 5 处 `_ = utiljson.Unmarshal`：**不是缺陷**（有据）

文档把它们列为"解析失败后继续用零值结构体判定"。实际读完整判定链后确认**危害不成立**：

零值只会让 `code == ""`、`FileCount == nil`、`shareStatus == ""` 三个分支被跳过，最终落到
`case statusCode != http.StatusOK` 或 `default`，两者都返回 `checkStateUncertain`——
**解析失败不会伪装成"链接有效"或"链接失效"，它落在一个安全的不确定态**。

而且这本来就是**机会式解析**：aliyun 的响应可能是 HTML 而非 JSON，解析失败是正常情形，
所以判定必须同时依赖 HTTP 状态码与解析出的字段（函数签名里的 `statusCode` 正说明这点）。
把 `_ =` 改成"解析失败即报错"反而会破坏正常路径。

结论：保持原样，**记录为"非缺陷·机会式解析"**。这是本次治理里第四次"看起来像缺陷、查完发现
需要证据"的情形。

### bolt 读取事务：真吞错，已修

`_ = s.cacheDB.View(...)`：表现出来只是"缓存未命中"，看起来一切正常，**实际 DB 损坏/关闭时
每次检查都会重读失败、且没有任何线索**。已改为记录日志。

同时修掉内层更隐蔽的一处：`decodeCachedCheckEntry` 失败原本 `return nil`，把**解码失败也伪装成
未命中**——损坏的条目会被永久静默忽略。改为向上返回，由事务把它当错误交给外层记录。

## 四十五、吞错处置（三）：panlian 用户状态持久化 5 处

5 处 `_ = p.saveUser(user)`（搜索成功更新最后访问时间、登录失效置 expired、relogin 成功/失败、
状态查询时新建用户）。危害是**重启后才显现**：内存状态已更新，当前进程一切正常，但持久化失败时
更改会丢失——新登录的用户会变回 `pending`、relogin 拿到的 cookie 会消失——而且没有任何线索。

与 §四十三 的磁盘写属同一类：**操作本身已经成功（搜索成功、登录成功），错误没法回传给调用方**，
所以处置是让它可观测，而不是把错误抛出去（那会把成功的搜索变成失败，是更糟的取舍）。

抽成 `saveUserOrLog`，失败时打印并说明后果（"重启后可能丢失登录态"），避免 5 处各写一遍。
这里**不需要限流**：saveUser 的频率是"每次搜索成功/登录"，不是每次结果，不会刷爆日志。
